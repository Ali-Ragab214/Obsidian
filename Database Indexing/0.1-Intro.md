
# 1. يعني إيه Database Indexing؟

تخيل إن عندك جدول `users` فيه مليون مستخدم، وعايز تجيب المستخدم اللي رقمه `500000`.

## الطريقة الأولى: Full Table Scan

تخيل إن الجدول عبارة عن كتاب ضخم، وكل صفحة فيها مجموعة من المستخدمين، وإنت بتدور على مستخدم معين من غير فهرس.

من غير Index: الـ Database ممكن تحتاج تفحص صفحات كتير لحد ما تلاقي الصف المطلوب.

ده اسمه Full Table Scan: الـ Database بتفحص بيانات الجدول عشان تلاقي الصفوف اللي بتحقق الشرط.

ولو مفيش Index مناسب، ممكن تضطر تقرأ جزء كبير من الجدول أو الجدول كله. لكن مش معنى كده إن كل Query من غير Index لازم تعمل Full Scan؛ الـ Query Optimizer هو اللي بيختار خطة التنفيذ.

## الطريقة التانية: باستخدام Index

الـ Index زي فهرس الكتاب: بدل ما تقرأ كل الصفحات، تدور في الفهرس وتوصل للمكان المطلوب.

الفكرة المهمة: الـ Index بيخلي الوصول للبيانات أسرع غالبًا، لكنه مش مجاني؛ بيستهلك مساحة إضافية وبيحتاج تحديث مع عمليات `INSERT` و`UPDATE` و`DELETE`.

# 4. أنواع الـ Indexes: Clustered vs Nonclustered

دي من أهم النقاط في المقدمة بتاعتك.

## أولًا: Clustered Index

في أنظمة زي SQL Server، الـ Clustered Index بيحدد تنظيم صفحات بيانات الجدول وفقًا لمفتاح الـ Index.

تخيل عندنا:

```
CREATE CLUSTERED INDEX idx_users_id
ON users(id);
```


الرسم المفاهيمي هيكون كده: 

Clustered Index

الترتيب حسب id

Data Page 1

id = 10

id = 20

id = 30

Data Page 2

id = 40

id = 50

id = 60

تصور مبسط للتنظيم المنطقي للبيانات، وليس شكل الصفحات الداخلي الدقيق.

لما تعمل Query زي دي:

```
SELECT *
FROM users
WHERE id = 50;
```

الـ Database تقدر تتنقل في الـ Index لحد ما توصل للصفحة اللي فيها `id = 50`، بدل ما تفحص كل الصفوف.

مهم جدًا: الـ Clustered Index مش شرط يكون `Unique`، لكن لو المفتاح مش Unique، نظام زي SQL Server بيستخدم قيمة إضافية داخلية للتمييز بين الصفوف المتساوية. وكمان مش شرط يكون الـ Index على الـ Primary Key، رغم إن ده اختيار شائع.

## ثانيًا: Nonclustered Index

ده Index منفصل عن تنظيم بيانات الجدول الأساسي، وبيحتوي على مفاتيح الـ Index ومعلومات الوصول للصفوف.

مثلًا:

```
CREATE INDEX idx_users_salary
ON users(salary);
```

تخيل إن عندنا البيانات دي:

|id|name|salary|
|---|---|---|
|10|Ali|40000|
|20|Sara|20000|
|30|Ahmed|35000|
|40|Mona|25000|

الـ Nonclustered Index على `salary` ممكن يكون بالشكل المفاهيمي ده:

Nonclustered Index على salary

20000

Row locator: 20

25000

Row locator: 40

35000

Row locator: 30

40000

Row locator: 10

كل قيمة Salary مرتبطة بمعلومة توصلنا للصف المناسب. شكل الـ Row Locator يعتمد على نوع قاعدة البيانات.

لما تنفذ:

```
SELECT *
FROM users
WHERE salary = 35000;
```

الـ Database تبحث في الـ Index عن `35000`، وبعدها تستخدم الـ Row Locator للوصول لبيانات Ahmed.

في SQL Server، لو الجدول عنده Clustered Index، الـ Row Locator في الـ Nonclustered Index غالبًا بيكون مفتاح الـ Clustered Index. أما لو الجدول Heap، بيكون فيه Heap RID.

### مقارنة سريعة

|النقطة|Clustered|Nonclustered|
|---|---|---|
|تنظيم بيانات الجدول|بيحدد تنظيمها حسب المفتاح|منفصل عن تنظيم البيانات الأساسي|
|عددها في SQL Server|واحد كحد أقصى لكل جدول|ممكن يكون فيه أكتر من واحد|
|يحتاج مساحة إضافية|له بنية Index وصفحات بيانات منظمة|يحتاج بنية إضافية لتخزين المفاتيح ومعلومات الوصول|
|Unique؟|ممكن Unique أو Nonunique|ممكن Unique أو Nonunique|

خلي بالك: تفاصيل الـ Clustered Index بتختلف بين أنظمة قواعد البيانات؛ مصطلح Heap والـ Clustered Index بالطريقة دي مرتبط خصوصًا بـ SQL Server.

# 5. ندخل بقى على الـ B-Tree

دي أهم حتة في المقدمة كلها.

في ملفك، إنت بدأت بالـ Binary Search Tree (BST)، وبعدها Balance Tree، وبعدها أشرت إلى إن الـ Index مش Binary Search Tree، وإن الـ B+ Tree بتخزن البيانات في الـ Leaf Nodes.

0-Intro.pdf

خلينا نبني الفكرة واحدة واحدة.

## أولًا: Binary Search Tree (BST)

الـ BST عبارة عن Tree، وكل Node فيها قيمة، والقاعدة الأساسية:

- القيم الأصغر بتكون ناحية الشمال.
    
- القيم الأكبر بتكون ناحية اليمين.
    

مثلًا، لو دخلنا القيم `50, 30, 70, 20, 40, 60, 80`:

![[Pasted image 20261013181146.png]]

كل Node عندها بحد أقصى طفلين: Left Child وRight Child.

لو عايز تدور على `60`:

1. تبدأ من `50`.
    
2. لأن `60 > 50` تروح يمين لـ `70`.
    
3. لأن `60 < 70` تروح شمال.
    
4. تلاقي `60`.
    

بدل ما تفحص كل القيم، بتستبعد أجزاء من الشجرة في كل خطوة.

لو الشجرة متوازنة، البحث ممكن يكون \(O(\log N)\). لكن لو الشجرة بقت مائلة جدًا، ممكن يوصل لـ \(O(N)\).

## طيب، إيه المشكلة في BST بالنسبة للـ Database؟

الـ Database مش بتتعامل مع كل قيمة كأنها موجودة في RAM بشكل منفصل؛ هي بتتعامل مع صفحات تخزين، والوصول لصفحات جديدة ممكن يكون مكلفًا.

لو عندك مليون قيمة، وبتستخدم شجرة Binary، كل Node فيها طفلين فقط. بالتالي ممكن تحتاج مستويات كتير نسبيًا للوصول للقيمة.

هنا تظهر فكرة الـ B-Tree.

## ثانيًا: B-Tree — الفكرة الأساسية

بدل ما كل Node تحتوي على Key واحدة أو اثنين من الأبناء، الـ B-Tree بتسمح إن كل Node تحتوي على عدة Keys وعدة Children، وفقًا لقواعد الشجرة.
![[Pasted image 20261013181351.png]]

مثلًا:

30 | 60

Root Node

10 | 20

Child 1

40 | 50

Child 2

70 | 80

Child 3

مثال مبسط للتوضيح؛ كل Child بتغطي نطاق قيم مختلف.

بما إن الـ Root فيها `30` و`60`، نقدر نقسم البحث لثلاثة نطاقات:

- أقل من `30` → أول Child.
    
- بين `30` و`60` → ثاني Child.
    
- أكبر من `60` → ثالث Child.
    

لاحظ إننا قدرنا نوجّه البحث لثلاثة فروع من Node واحدة، مش فرعين بس.

ملحوظة دقيقة: الـ B-Tree مش معناها إن كل Node لازم يكون فيها أكتر من Key، لكن تصميمها يسمح بكده. وكل المفاتيح داخل الشجرة بتخضع لقواعد الترتيب والتوازن الخاصة بها.

## ثالثًا: ليه الـ B-Tree مناسبة للـ Database؟

لأننا نقدر نحط عددًا كبيرًا من المفاتيح والـ Pointers داخل Page واحدة.

بدل ما كل مستوى في الشجرة يوصلك لاختيار واحد من فرعين، ممكن يوصلك لاختيار واحد من عشرات أو مئات الفروع، حسب حجم الـ Keys والـ Pointers وحجم الـ Page.

المقارنة في شكل الشجرة

Binary Tree

كل Node لها طفلان كحد أقصى

B-Tree

مفاتيح وفروع أكتر في كل Node

النتيجة: الشجرة ممكن تبقى أقصر، وبالتالي تقل عدد مستويات الـ Index والـ Page accesses المطلوبة للبحث.

وده السبب إن الـ B-Tree وعائلتها من أشهر هياكل البيانات المستخدمة في الـ Database Indexes.

# 6. طيب إيه الفرق بين B-Tree وB+ Tree؟
![[Pasted image 20261013182010.png]]

دي نقطة مهمة لأن ملفك بينتهي عند الـ B+ Tree.

الـ B+ Tree نوع من الأشجار المتوازنة متعددة الفروع، لكنه بيتميز عن الشكل التقليدي للـ B-Tree بطريقة تنظيم البيانات.

## B-Tree

في الشكل التقليدي للـ B-Tree، ممكن تكون البيانات أو الـ Records مرتبطة بمفاتيح موجودة في Nodes داخلية أو في الـ Leaves، حسب التصميم.

## B+ Tree

في الـ B+ Tree، كل مفاتيح البيانات الفعلية أو مراجع السجلات   ==🔵(Data)==  تكون في الـ Leaf Nodes، أما الـ Internal Nodes فوظيفتها الأساسية توجيه البحث.

وكمان الـ Leaf Nodes غالبًا بتكون مرتبطة ببعض في الاتجاهين، وده اللي مذكور في ملفك باسم `Doubly Linked List`.

0-Intro.pdf

B+ Tree — شكل توضيحي

30 | 60

Internal Node

10 | 20

Leaf

30 | 40 | 50

Leaf

60 | 70 | 80

Leaf

روابط بين الـ Leaves لتسهيل المرور على القيم المتتابعة.

الرسم للتوضيح فقط، مش بنية فعلية دقيقة لصفحات SQL Server أو PostgreSQL. كمان في الـ B+ Tree، الـ Internal Nodes ممكن تكرر بعض مفاتيح الـ Leaves كمفاتيح توجيه، وده طبيعي.

## ليه الـ B+ Tree مهمة جدًا في الـ Database؟

خلينا نقارن عمليتين:

1. البحث عن قيمة واحدة

```
SELECT *
FROM users
WHERE id = 500;
```

الـ Database تنزل من الـ Root، تعدّي على عدد قليل من الـ Internal Nodes، وبعدها توصل للـ Leaf المناسبة، ومنها لبيانات الصف.

2. البحث عن Range من القيم

```
SELECT *
FROM users
WHERE id BETWEEN 500 AND 1000;
```

بعد ما توصل لأول Leaf فيها قيمة مناسبة، تقدر تكمل على الـ Leaf Nodes المجاورة باستخدام الروابط بينها، بدل ما ترجع للـ Root وتعيد البحث عن كل قيمة من الصفر.

وده بيخلي الـ B+ Tree مناسبة جدًا لعمليات الـ Range Queries والـ Sorting في حالات كتير.

# 8. نطبّق على الـ Query الموجودة في ملفك

إنت كاتب المثال ده:

0-Intro.pdf

```
SELECT *
FROM users
WHERE salary > 30000;
```

لو مفيش Index مناسب، الـ Database ممكن تعمل Full Table Scan وتفحص الصفوف لتحدد مين راتبه أكبر من `30000`.

لكن لو عندك Index على `salary`:

```
CREATE INDEX idx_users_salary
ON users(salary);
```

ممكن تستخدم الـ Index للوصول للقيم الأكبر من `30000`، ثم تجيب الصفوف المطلوبة.

لكن هل وجود Index معناه إنه لازم يُستخدم؟ لأ.

الـ Query Optimizer بيختار الخطة بناءً على عوامل، منها:

- عدد الصفوف المتوقع إنها تطابق الشرط.
    
- حجم الجدول.
    
- هل الـ Index بيغطي الأعمدة المطلوبة ولا هيحتاج عمليات وصول إضافية للجدول؟
    
- تكلفة قراءة الصفحات من التخزين أو الـ Cache.
    

لو معظم المستخدمين رواتبهم أكبر من `30000`، ممكن الـ Full Table Scan يكون أوفر من استخدام الـ Index والرجوع للجدول صفًا صفًا. ولو الاستعلام بيطلب `SELECT *`، فالـ Index على `salary` وحده مش بيحتوي بالضرورة على كل الأعمدة المطلوبة.

# 9. الخلاصة اللي تحفظها للإنترفيو

Indexing

طريقة لتنظيم مفاتيح ومعلومات الوصول للبيانات بهدف تسريع البحث، مع تكلفة إضافية في المساحة وتحديثات الكتابة.

Pages

وحدات التخزين التي يتعامل معها محرك قاعدة البيانات؛ الصفوف تُقرأ وتُفحص داخل هذه الصفحات.

B-Tree

شجرة متوازنة متعددة الفروع تسمح بمفاتيح متعددة في الـ Node، وتقلل عدد المستويات اللازمة للبحث.

B+ Tree

الـ Internal Nodes للتوجيه، ومفاتيح البيانات أو مراجع السجلات في الـ Leaves، التي ترتبط عادةً ببعضها لتسهيل الـ Range Queries.

Clustered vs Nonclustered

الأول ينظم بيانات الجدول وفق مفتاحه في أنظمة مثل SQL Server؛ الثاني بنية Index منفصلة تساعد على الوصول للصفوف.
