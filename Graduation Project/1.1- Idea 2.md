تمام، خليني أشرحلك المشروع بالكامل من الأول للآخر عشان تبقى فاهم كل حاجة قبل ما نبدأ نكود.

## المشروع باختصار: إيه هو StockSavvy؟

نظام إدارة مخزون (Inventory Management) لكن الفكرة الأساسية بتاعته مش المخزون نفسه، دي بس "البنية التحتية" اللي لازم تكون موجودة. **جوهر المشروع الحقيقي هو الـ AI Agents** اللي بتتعامل مع المخزون ده بشكل ذكي وبتاخد قرارات (بموافقة بشرية) زي التنبؤ بالطلب والتفاوض مع الموردين واكتشاف الغش.

المستندات قسّمت المشروع لـ 3 مستويات:

### 1. MVP (الأساس اللي لازم يتعمل الأول)

ده الجزء "العادي" اللي مفيهوش AI: تسجيل دخول وصلاحيات (مدير/موظف)، منتجات، حركة مخزون (كل تغيير بيتسجل كـ event مش بس رقم بيتغير)، موردين، دورة حياة أمر الشراء (PO) من مسودة لحد الاستلام، تنبيهات نقص المخزون، وداشبورد بسيط.

**ليه ده مهم:** من غير البيانات دي، الـ Agents مش هتلاقي حاجة تشتغل عليها. يعني لازم تعمل الجزء ده وتحطله بيانات وهمية (demo data) الأول.

### 2. Core AI (ده هو المشروع الحقيقي)

أربع Agents + نظام RAG:

**أ. RAG Assistant (شات بوت للمدير)** بيرد على أسئلة زي "إيه أرخص سعر اشتريناه بيه المنتج ده قبل كده؟" أو "مين أرخص مورد للفئة دي؟" — بيدور في العقود والفواتير القديمة وتاريخ الحركات ويجيب إجابة مبنية على بيانات حقيقية (مش هلوسة).

**ب. Demand Forecasting Agent (التنبؤ بالطلب)** بياخد بيانات المبيعات القديمة ويتوقع الطلب المتوقع في الأسابيع الجاية. **ده Agent مستقل تمامًا** — مش محتاج موافقة، لأنه بس بيعرض معلومة مش بياخد قرار.

**ج. Reorder Agent (إعادة الطلب التلقائي)** لما المخزون ينزل تحت حد معين، الـ Agent ده بيعمل مسودة أمر شراء (PO) — بيحدد الكمية والمورد الأنسب. **لازم موافقة المدير** قبل ما يتحول لأمر شراء فعلي.

**د. Vendor Negotiation Agent (التفاوض مع الموردين) — ده نجم المشروع** ده مش استدعاء واحد للـ LLM، ده Agent متعدد الخطوات وله حالة (stateful):

1. يجمع معلومات عن المورد ده (أسعار سابقة، عقود) عن طريق RAG
2. يقترح عرض افتتاحي
3. **checkpoint موافقة بشرية** — المدير لازم يوافق قبل ما أي حاجة "تتبعت" للمورد
4. يستقبل رد مقابل (simulated لأن التكامل الحقيقي مع الموردين stretch goal)
5. يقيّم الرد ده مقابل معايير قبول محددة
6. يكرر الخطوات 3-5 لحد ما يوصلوا لاتفاق أو يوصلوا لحد أقصى من الجولات
7. يحول النتيجة لأمر شراء نهائي

كل خطوة بتتسجل بالكامل (audit trail) — وده اللي هتعرضه في المناقشة.

**هـ. Anomaly/Fraud Detection Agent (اكتشاف الشذوذ)** بيراقب سجل حركة المخزون وبيلاقي أنماط مشبوهة (نقص مفاجئ، تعديلات في وقت غريب، إلخ). **مهم جدًا: الـ Agent ده منه أبدًا يصحح البيانات أو يوقف مستخدم** — بس بيعمل "علم" (flag) للمراجعة البشرية مع شرح ليه هو مشبوه.

### 3. Stretch Goals (لو فاضلك وقت)

دعم أكتر من فرع، تواصل حقيقي مع الموردين بالإيميل، إشعارات، تطبيق PWA للموظفين، تقارير BI.

## البنية المعمارية (Architecture)

هنا فيه نقطة **مهمة جدًا لازم تاخد قرار فيها**:

|الطبقة|الاختيار|
|---|---|
|Backend|**NestJS** (TypeScript)|
|Frontend|**React**|
|قاعدة البيانات|⚠️ **متعارضة بين مستندين**|
|Cache/Queue|Redis + BullMQ|
|LLM|Anthropic أو OpenAI عن طريق `AgentsModule`|
|Containerization|Docker Compose|

### ⚠️ تعارض في قاعدة البيانات

- المستند التاني (`02-architecture.md`) بيقول: **PostgreSQL + pgvector** في نفس القاعدة (سبب منطقي: أقل تعقيد، اتساق معاملاتي، حجم بياناتك صغير أصلاً).
- المستند السادس (`06-mongodb-schema.md`) بيقول صراحة إنه **بيستبدل** التوصية دي بـ **MongoDB 8.2** اللي فيه `$vectorSearch` أصلي من غير Atlas.

يعني عندك مستندين بيقترحوا حلين مختلفين لنفس المشكلة، وأنت لازم تختار واحد قبل ما نبدأ نكود، لأن السكيما والكويريز مختلفة تمامًا بين الاتنين.

### طبقة الـ Agents (الجزء الأهم في الـ Backend)

- كل Agent (`ForecastingAgent`, `ReorderAgent`, `NegotiationAgent`, `AnomalyAgent`) بيطبق interface موحد وله `runId`.
- فيه **State Machine** لكل تشغيلة، خصوصًا Negotiation Agent.
- الشغل الطويل (زي جولات التفاوض) بيمشي عن طريق **BullMQ jobs** مش synchronous HTTP، عشان تقدر تعرض "الـ Agent بيفكر..." في الواجهة.
- فيه **Approval Queue واحدة مشتركة** كل الـ Agents بتستخدمها — مش 4 أنظمة موافقة منفصلة. ده أهم قرار معماري في المشروع كله.

### نمط الكود الفعلي لكل Agent

كل الـ Agents بتتبني على نفس اللوب:

```
اجمع context (عن طريق tool calls) → اطلب من الـ LLM قرار منظم (JSON) → سجل في audit log → لو محتاج موافقة، اوقف وسجل ApprovalRequest → وإلا نفذ القرار
```

اللي بيخلي الموضوع "قابل للبناء فعليًا" (مش بس شات بوت بتتمنى يتصرف صح) هو إنه في كل نقطة قرار، الـ LLM بيرجع JSON منظم (زي `NegotiationDecision` بفيلد `action`, `reasoning`, `needsApproval`) مش نص حر.

## سيناريو العرض في المناقشة (Demo Story)

المستندات بتقترح سيناريو واحد متصل بدل ما تعرض كل feature لوحده: المدير تفتح الداشبورد → تلاقي SKU تحت حد إعادة الطلب → Reorder Agent يعمل مسودة PO → المدير تختار تفاوض بدل الموافقة المباشرة → Negotiation Agent يقترح عرض مبني على تاريخ حقيقي → موافقة → رد من المورد (وهمي) → اتفاق → PO نهائي → المدير تسأل الشات بوت عن السعر اللي اتفقوا عليه ويجيبلها إجابة من الترانسكريبت اللي اتعمل لسه → في نفس اليوم، Anomaly Agent يكتشف حركة مشبوهة في SKU تاني.

السيناريو ده بيوري الـ 4 Agents + RAG + human-in-the-loop في قصة واحدة.
