# Stock Movement Ledger — الشرح الأعمق (Logic + Module Structure)

هفصلها في 3 أجزاء: **المشكلة الحقيقية اللي بتحلها بعمق**، **اللوجيك اللي المفروض يتنفذ خطوة بخطوة**، وأخيرًا **الـ NestJS module structure الكامل**.

---

## 1️⃣ الفكرة الأعمق: ليه مش مجرد `UPDATE quantity`؟

المشكلة الحقيقية مش بس "عايز أعرف التاريخ"، المشكلة هي **Race Condition** و **Concurrency**.

تخيل السيناريو ده:

- عندك SKU فيه `quantity = 5`
- جيلك طلبين في نفس اللحظة بالظبط، كل واحد عايز ياخد 3 وحدات
- Request A: بيقرا الكمية (5) → يحسب (5-3=2) → يكتب 2
- Request B: بيقرا الكمية (5) في نفس اللحظة **قبل ما A يكتب** → يحسب (5-3=2) → يكتب 2

**النتيجة الغلط:** الكمية بقت 2 بدل ما تبقى -1 (يعني باعت 6 وحدات من أصل 5!). ده اسمه **Lost Update Problem**.

الـ Ledger لوحده مش هيحل المشكلة دي تلقائيًا — لازم تتعامل معاها بـ **Locking**. هوضحها في اللوجيك تحت.

## 2️⃣ اللوجيك التفصيلي (خطوة بخطوة)

### الخطوة 1: أي عملية بتغيّر المخزون لازم تعدي من نقطة واحدة بس

مينفعش أي service في النظام يعمل `save()` على الـ Sku ويغير الـ quantity مباشرة. لازم يبقى فيه **method واحدة مركزية**: `recordMovement()`.

### الخطوة 2: Transaction + Row-Level Locking

```typescript
async recordMovement(skuId: string, type: MovementType, qty: number, referenceId?: string) {
  return this.dataSource.transaction(async (manager) => {
    // 1. اقفل الـ row بتاع الـ SKU لحد ما الـ transaction تخلص (Pessimistic Lock)
    const sku = await manager.findOne(Sku, {
      where: { id: skuId },
      lock: { mode: 'pessimistic_write' }, // مهم جدًا هنا
    });

    if (!sku) throw new NotFoundException('SKU not found');

    // 2. احسب الرصيد الجديد
    const newBalance = sku.currentStock + qty;

    // 3. Business rule: ميسمحش برصيد سالب
    if (newBalance < 0) {
      throw new BadRequestException(
        `Insufficient stock. Available: ${sku.currentStock}, Requested: ${Math.abs(qty)}`
      );
    }

    // 4. سجّل الحركة في الـ Ledger (append-only، أبدًا متتعدلش)
    const movement = manager.create(StockMovement, {
      sku: { id: skuId },
      type,
      quantityChange: qty,
      balanceAfter: newBalance,
      referenceId,
    });
    await manager.save(movement);

    // 5. حدّث الـ cache column (denormalized) على الـ Sku عشان القراءة تبقى سريعة
    sku.currentStock = newBalance;
    await manager.save(sku);

    return movement;
  });
}
```

**ليه الـ Lock مهم:** `pessimistic_write` بيخلي أي transaction تانية عايزة تعدل نفس الـ SKU **تستنى** لحد ما الأولى تخلص (commit أو rollback). كده Request B هيستنى A يخلص، وبعدين هيقرا الرصيد الصح (2) مش القديم (5).

### الخطوة 3: الفرق بين "الرصيد الحالي" و"إعادة الحساب"

- **الطريقة السريعة (اللي فوق):** عمود `currentStock` بيتحدث مع كل حركة داخل نفس transaction — ده اللي هتستخدمه في 99% من الحالات (API responses سريعة).
- **الطريقة الدقيقة (للـ audit/reconciliation):** لو حصل شك إن فيه bug أو تلاعب، تقدر تعيد حساب الرصيد من الصفر:

```sql
SELECT sku_id, SUM(quantity_change) as calculated_balance
FROM stock_movement
WHERE sku_id = :id
GROUP BY sku_id;
```

لو الرقم ده مايطابقش عمود `currentStock`، معناها فيه bug حصل تعديل مباشر من مكان غلط.

### الخطوة 4: كل نوع عملية في النظام بيستدعي `recordMovement` بدل ما يلمس الـ Sku

مثال: لما حد يعمل Order:

```typescript
// في OrderService، مش في SkuService مباشرة
await this.stockMovementService.recordMovement(
  skuId,
  MovementType.SALE_OUT,
  -quantity, // سالب لأنه خروج
  order.id,   // reference للـ order اللي سبب الحركة
);
```

## 3️⃣ الـ NestJS Module Structure

```
src/
└── stock-movement/
    ├── stock-movement.module.ts
    ├── stock-movement.controller.ts
    ├── stock-movement.service.ts
    │
    ├── entities/
    │   └── stock-movement.entity.ts
    │
    ├── enums/
    │   └── movement-type.enum.ts
    │
    ├── dto/
    │   ├── create-movement.dto.ts     // internal use (مش endpoint عام غالبًا)
    │   ├── movement-response.dto.ts
    │   └── movement-query.dto.ts      // للفلترة (date range, sku, type)
    │
    └── mappers/

```

### الـ Controller — endpoints للقراءة بس (مفيش POST مباشر للـ movement من برا)

```typescript
@Controller('stock-movements')
export class StockMovementController {
  @Get('sku/:skuId')
  getHistory(@Param('skuId', ParseUUIDPipe) skuId: string, @Query() query: MovementQueryDto) {
    return this.stockMovementService.getHistoryForSku(skuId, query);
  }

  @Get('sku/:skuId/reconcile')
  reconcile(@Param('skuId', ParseUUIDPipe) skuId: string) {
    return this.stockMovementService.reconcileBalance(skuId);
  }
}
```

**ليه مفيش `POST /stock-movements` مباشر؟** لأن الحركات لازم تحصل نتيجة عملية بيزنس حقيقية (Order، Purchase، Adjustment)، مش endpoint عام أي حد يبعتله. لو محتاج adjustment يدوي (جرد فعلي مثلًا)، تعمله من خلال endpoint متخصص زي `POST /inventory/adjust` بيستدعي `recordMovement` من جوه.

## خلاصة سريعة للإنترفيو

> "الـ Stock Movement Ledger مش بس تسجيل تاريخي — هو مصدر الحقيقة الوحيد للمخزون. أي تغيير في الكمية لازم يعدي من خلاله جوه transaction واحدة مع pessimistic locking عشان أمنع الـ race conditions لو جالي طلبات متزامنة على نفس الـ SKU. الـ `currentStock` على جدول الـ Sku هو مجرد cache بيتحدث في نفس الـ transaction، لكن لو حصل شك في دقته، بقدر أعيد حسابه من مجموع الحركات في الـ ledger نفسه."
