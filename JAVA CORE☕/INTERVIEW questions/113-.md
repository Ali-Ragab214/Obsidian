# **1. الفرق بين** `==` **و** `equals()`

عندنا نوعين من المساواة:

- **Reference Equality:** هل المتغيرين بيشاوروا على نفس الـ Object في الذاكرة؟
    
- **Logical Equality:** هل الـ Objects بيمثلوا نفس القيمة أو نفس المعنى؟
    

مثال:

```java
String s1 = new String("Ali");
String s2 = new String("Ali");

System.out.println(s1 == s2);      // false
System.out.println(s1.equals(s2)); // true
```

إيه اللي حصل؟

**الـ Objects في الذاكرة**

**s1**

# **Object A**

"Ali"

**s2**

# **Object B**

"Ali"

`s1 == s2`

false

مختلفين في الـ Reference.

`s1.equals(s2)`

true

نفس المحتوى المنطقي.

**أول قاعدة:**

`==` مع الـ Objects بيقارن الـ References، مش محتوى الـ Objects.

أما `equals()` فهي method موجودة في `Object`، والـ Default Implementation بتاعتها بتتصرف زي `==`.

لكن Classes زي `String` بتعمل Override ليها علشان تقارن المحتوى.

مثال تاني:

```java
Object a = new Object();
Object b = new Object();

System.out.println(a.equals(b)); // false
```

لأن `Object.equals()` الافتراضية بتقارن الـ References.

# **2. طيب إيه علاقة** `hashCode()` **بالموضوع؟**

كل Object عنده method اسمها:

```java
public int hashCode()
```

بترجع قيمة من نوع `int`، بنستخدمها في تحديد المكان المحتمل للـ Object داخل Hash-based Collections.

مثلاً:

```java
String s1 = new String("Ali");
String s2 = new String("Ali");ي

System.out.println(s1.equals(s2));    // true
System.out.println(s1.hashCode());    // Same value
System.out.println(s2.hashCode());    // Same value
```

ليه الـ HashCode متساوي؟

لأن `String` عملت Override للـ `equals()` و`hashCode()` بحيث الاتنين بيعبروا عن نفس المحتوى.

لكن خلي بالك:

**الـ HashCode مش Unique ID للـ Object.**

ممكن Objectين مختلفين يكون ليهم نفس الـ HashCode.

وده اسمه:

**Hash Collision**

مثال مشهور:

```java
String s1 = "FB";
String s2 = "Ea";

System.out.println(s1.equals(s2));    // false
System.out.println(s1.hashCode());    // 2236
System.out.println(s2.hashCode());    // 2236
```

الاتنين عندهم نفس الـ HashCode، لكن مش متساويين.

إذن:

- Same `equals()` → لازم Same `hashCode()`.
    
- Same `hashCode()` → مش شرط Same `equals()`.
    

دي أهم قاعدة في المنظومة كلها.

# **3. الـ Contract بين equals و hashCode**

Java بتفرض Contract لازم تلتزم بيه.

|القاعدة|معناها|
|---|---|
|Reflexive|`x.equals(x)` لازم تكون true|
|Symmetric|لو `x.equals(y)` true، يبقى `y.equals(x)` true|
|Transitive|لو x=y وy=z، يبقى x=z|
|Consistent|طالما بيانات المقارنة ثابتة، النتيجة ثابتة|
|Non-null|`x.equals(null)` لازم تكون false|

وبالنسبة للـ `hashCode()`:

1. لو Objectين متساويين باستخدام `equals()`، لازم يكون ليهم نفس الـ HashCode.
    
2. لو Objectين ليهم نفس HashCode، مش شرط يكونوا متساويين.
    
3. طالما البيانات المستخدمة في المقارنة متغيرتش، الـ HashCode لازم يفضل ثابت خلال تشغيل التطبيق.
    

# **4. إيه اللي بيحصل جوه HashMap؟**

دي أهم نقطة في السؤال.

خلينا نفهم إزاي `HashMap` بتخزن البيانات.

```
Map<String, Integer> map = new HashMap<>();

map.put("Ali", 100);
map.get("Ali");
```

لما تعمل `put()`، الـ HashMap بتعمل تقريباً الخطوات دي:

## **HashMap.put(key, value)**

1. **Calculate Hash**
    
    تستدعي `hashCode()` للـ Key، وتستخدمه لحساب Hash داخلي.
    
2. **Find Bucket**
    
    تستخدم الـ Hash لتحديد الـ Bucket المناسبة داخل الـ Internal Array.
    
3. **Check Existing Keys**
    
    لو الـ Bucket فيها عناصر، تقارن الـ Hash وبعدها الـ Keys باستخدام `equals()` عند الحاجة.
    
4. **Insert or Update**
    
    لو لقت Key متساوية، بتحدّث الـ Value. لو ملقتش، بتضيف Entry جديدة.
    

تبسيط لمسار HashMap الداخلي، مع إغفال بعض تفاصيل الـ Hash Spreading والـ Tree Bins.

تخيل إن عندك مخزن فيه أدراج.

- `hashCode()` بيساعدك تعرف أنهي درج تروحله.
    
- `equals()` بتساعدك تعرف هل العنصر اللي جوه الدرج هو نفس الـ Key اللي بتدور عليه ولا لأ.
    

الـ HashCode بيوصلك للمكان المحتمل، والـ equals بتحسم المساواة.

# **5. ماذا يحدث لو عملت Override لواحد بس؟**

هنا بقى لب السؤال.

## **الحالة الأولى: عملت Override لـ equals() فقط**

مثال:

```java
class Employee {

    private int id;

    Employee(int id) {
        this.id = id;
    }

    @Override
    public boolean equals(Object obj) {
        if (this == obj) return true;

        if (!(obj instanceof Employee other))
            return false;

        return this.id == other.id;
    }
}
```

عندنا:

```java
Employee e1 = new Employee(10);
Employee e2 = new Employee(10);

System.out.println(e1.equals(e2)); // true
System.out.println(e1.hashCode() == e2.hashCode());
```

إيه المشكلة؟

إحنا عملنا Override لـ `equals()`، لكن معملناش Override لـ `hashCode()`.

بالتالي كل Object هيستخدم الـ `hashCode()` الموروثة من `Object`، ومش مضمون إن الاتنين يطلعوا نفس القيمة.

دلوقتي:

```
Set<Employee> employees = new HashSet<>();

employees.add(e1);
employees.add(e2);

System.out.println(employees.size());
```

ممكن النتيجة تكون:

```
2
```

مع إن:

```
e1.equals(e2) == true
```

**ليه؟**

لأن الـ HashSet بدأت بالـ HashCode، وممكن كل Object يروح Bucket مختلفة.

وبالتالي مش هتحتاج تقارن `equals()` بين الاتنين أصلاً.

**Scenario: Override equals() فقط**

**e1**

# **ID 10**

Hash A

Bucket 2

**e2**

# **ID 10**

Hash B

Bucket 5

HashSet may contain both

رسم توضيحي لاحتمال اختلاف الـ HashCode، مش قيم مضمونة.

إذن القاعدة: لو عملت Override لـ `equals()` لازم تعمل Override لـ `hashCode()` معاها.

## **الحالة الثانية: عملت Override لـ hashCode() فقط**

مثال:

```
class Employee {

    private int id;

    Employee(int id) {
        this.id = id;
    }

    @Override
    public int hashCode() {
        return Integer.hashCode(id);
    }
}
```

دلوقتي:

```
Employee e1 = new Employee(10);
Employee e2 = new Employee(10);

System.out.println(e1.hashCode() == e2.hashCode()); // true
System.out.println(e1.equals(e2));                  // false
```

ليه `equals()` طلعت false؟

لأننا لسه بنستخدم `Object.equals()` الافتراضية، اللي بتقارن References.

لما نعمل:

```
Set<Employee> employees = new HashSet<>();

employees.add(e1);
employees.add(e2);

System.out.println(employees.size()); // 2
```

الـ HashSet هتلاقي إن الاتنين في نفس الـ Bucket، لكنها لما تستدعي `equals()` هتلاقيهم مختلفين.

وبالتالي هتسمح بتخزين الاتنين.

**الخلاصة:** نفس الـ HashCode مش معناه إن الـ Objects متساوية.

## **مقارنة الحالتين**

|Override|النتيجة|
|---|---|
|equals فقط|ممكن Objects متساوية تتخزن مرتين|
|hashCode فقط|Objects مختلفة منطقياً ممكن تشترك في نفس Hash|
|الاتنين|الـ Hash Collections تشتغل صح|
|ولا واحد|Default reference equality|

# **6. إيه قصة Mutable Keys؟**

دي من أخطر المشاكل في `HashMap`.

تخيل عندك:

```
class Employee {

    int id;

    Employee(int id) {
        this.id = id;
    }

    @Override
    public boolean equals(Object obj) {
        if (!(obj instanceof Employee other))
            return false;

        return id == other.id;
    }

    @Override
    public int hashCode() {
        return Integer.hashCode(id);
    }
}
```

واستخدمناه كـ Key:

```
Employee e1 = new Employee(10);

Map<Employee, String> map = new HashMap<>();

map.put(e1, "Ali");
```

دلوقتي غيرنا الـ ID:

```
e1.id = 20;
```

وبعدين:

```
System.out.println(map.get(e1));
```

ممكن ترجع:

```
null
```

إزاي؟ ده نفس الـ Object!

هنا لازم نفهم إن الـ HashMap خزنت الـ Entry بناءً على الـ HashCode القديم.

لما غيرنا `id`، الـ HashCode اتغير.

فبالتالي `get()` بتدور في Bucket مختلفة عن اللي الـ Entry موجودة فيها.

**قبل التعديل**

id = 10

Bucket A

**بعد التعديل**

id = 20

Bucket B

الـ Entry لسه في Bucket A، لكن البحث بقى في Bucket B.

علشان كده:

**Never use mutable fields in equals/hashCode for objects used as HashMap keys or HashSet elements.**

الأفضل إنك تستخدم Immutable Keys.

# **7. getClass() vs instanceof في equals()**

الاتنين بيستخدموا لتحديد هل الـ Object اللي بنقارنه ينتمي لنفس النوع ولا لأ.

### **باستخدام getClass()**

```
if (obj == null || getClass() != obj.getClass())
    return false;
```

ده معناه لازم الاتنين يكونوا من نفس الـ Runtime Class بالضبط.

حتى لو واحد Child من التاني، المقارنة هترفض.

### **باستخدام instanceof**

```
if (!(obj instanceof Employee other))
    return false;
```

ده بيسمح بالـ Subclasses.

لكن هنا فيه مشكلة محتملة اسمها **Symmetry Violation**.

مثلاً:

```
class Employee {
    int id;

    Employee(int id) {
        this.id = id;
    }

    @Override
    public boolean equals(Object obj) {
        if (!(obj instanceof Employee other))
            return false;

        return id == other.id;
    }
}

class Manager extends Employee {

    Manager(int id) {
        super(id);
    }
}
```

لو عملنا:

```
Employee e = new Employee(10);
Manager m = new Manager(10);

System.out.println(e.equals(m)); // true
System.out.println(m.equals(e)); // true
```

في المثال ده النتيجة لسه Symmetric، لكن لو `Manager` عمل Override وأضاف شروط مقارنة خاصة بيه، ممكن تحصل:

```
e.equals(m) = true
m.equals(e) = false
```

وده بيكسر الـ Contract.

عشان كده `getClass()` اختيار أبسط في الـ Value Objects اللي مش محتاجة مساواة عبر الـ Inheritance، أما `instanceof` محتاجة تصميم دقيق للـ Equality Contract.

# **8. طب والـ Records؟**

Java Records بتوفر `equals()` و`hashCode()` تلقائياً.

مثلاً:

```
record Employee(int id, String name) {}

Employee e1 = new Employee(10, "Ali");
Employee e2 = new Employee(10, "Ali");

System.out.println(e1.equals(e2)); // true
System.out.println(e1.hashCode() == e2.hashCode()); // true
```

ليه؟

لأن الـ Record بتولد implementations بتعتمد على مكونات الـ Record (Components).

وده بيخليها مناسبة جداً للـ Immutable Data Objects.

لكن خلي بالك إن الـ Record مش بيضمن إن كل Component جواه Immutable؛ لو عندك mutable object، تفضل مشكلة التعديل ممكن تأثر على Equality وHashing.

# **9. أفضل طريقة لكتابة equals و hashCode**

بدل ما تكتب المنطق كله بنفسك، استخدم:

```
import java.util.Objects;

class Employee {

    private final int id;
    private final String name;

    Employee(int id, String name) {
        this.id = id;
        this.name = name;
    }

    @Override
    public boolean equals(Object obj) {

        if (this == obj) return true;

        if (!(obj instanceof Employee other))
            return false;

        return id == other.id
                && Objects.equals(name, other.name);
    }

    @Override
    public int hashCode() {
        return Objects.hash(id, name);
    }
}
```

`Objects.equals(a, b)` بتعمل Null-safe comparison.

و`Objects.hash(...)` بتحسب Hash بناءً على نفس الـ Fields اللي بنستخدمها في `equals()`.

المهم إن حقول المقارنة تكون متوافقة في الاتنين.

# **10. Interview Cheat Sheet**

احفظ الفكرة دي كويس:

|Concept|Responsibility|
|---|---|
|`==`|Compare references|
|`equals()`|Compare logical equality|
|`hashCode()`|Help locate objects in hash-based collections|
|HashMap|Uses hash first, then equality checks|
|HashSet|Uses HashMap internally|
|Collision|Different objects with same hash|
|Mutable Key|Can become unreachable through normal lookup|
|Record|Generates equals/hashCode automatically|

**أهم 3 جمل في الانترفيو:**

1. If two objects are equal according to `equals()`, they must have the same `hashCode()`.
    
2. Having the same hash code does not guarantee that two objects are equal.
    
3. Whenever we override `equals()`, we must also override `hashCode()` to preserve the contract and ensure correct behavior in hash-based collections.
