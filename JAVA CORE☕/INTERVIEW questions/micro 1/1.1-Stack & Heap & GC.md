# 1. Java Memory Model (Heap, Stack, Garbage Collection)

## What is Java Memory Model?

The **Java Memory Model (JMM)** defines how memory is organized and how Java threads interact with shared data. For interviews, when people ask about the Java Memory Model, they often expect you to explain **Stack Memory, Heap Memory, and Garbage Collection** (although the formal JMM also includes visibility, synchronization, and happens-before rules).

---

# Stack Memory

## What is Stack Memory?

Each **Thread** in Java has its **own Stack Memory**.

The stack stores:

- Local variables
    
- Method parameters
    
- Method call frames (Stack Frames)
    
- References to objects (not the objects themselves)
    

When a method is called, Java creates a new **Stack Frame**.

When the method finishes, its Stack Frame is automatically removed.

### Example

```java
public void method1() {
    int x = 10;
    method2();
}

public void method2() {
    int y = 20;
}
```

Memory:

```text
Thread Stack

--------------------
method2()
y = 20
--------------------
method1()
x = 10
--------------------
main()
--------------------
```

When `method2()` returns:

```text
Thread Stack

--------------------
method1()
x = 10
--------------------
main()
--------------------
```

The frame is automatically destroyed.

---

## Characteristics of Stack Memory

- Thread-specific
    
- Stores primitive local variables
    
- Stores object references
    
- Fast access
    
- Automatically managed
    
- Small in size
    

---

# Heap Memory

## What is Heap Memory?

Heap Memory stores **all Java Objects**.

Example:

```java
Student s = new Student();
```

Memory:

```text
Stack

s -----------+

              |

Heap          |

+-------------+

| Student     |

+-------------+
```

The variable `s` lives in the **Stack**.

The actual `Student` object lives in the **Heap**.

---

## Characteristics of Heap

- Shared among all threads
    
- Stores all objects
    
- Managed by Garbage Collector
    
- Larger than Stack
    
- Slightly slower than Stack
    

---

# Stack vs Heap

|Stack|Heap|
|---|---|
|Stores local variables|Stores objects|
|One per thread|Shared by all threads|
|Automatically cleared|Cleared by Garbage Collector|
|Very fast|Slower|
|Small size|Large size|

---

# Object Creation

Example:

```java
public static void main(String[] args) {

    Student s = new Student();

}
```

Memory

```text
Stack

main()

s ----------+

             |

+------------+

+------------+
```

When `main()` ends:

```text
Stack

(empty)
```

Now no reference points to the object.

The object becomes **eligible for Garbage Collection**.

# Garbage Collection (GC)

## What is Garbage Collection?

Garbage Collection is the JVM process that automatically removes objects that are no longer reachable.

It helps prevent memory leaks caused by forgotten deallocation (unlike C/C++).

---

## How does the GC know an object should be removed?

The Garbage Collector checks whether an object is **reachable**.

If **no live reference** points to an object, it becomes:

> **Eligible for Garbage Collection**

Example

```java
Student s = new Student();

s = null;
```

Memory

Before:

```text
Stack

s --------+

          |

Heap      |

Student Object
```

After:

```text
Stack

s = null

Heap

Student Object
```

No reference exists.

The object becomes eligible for GC.

---

# Reachable vs Unreachable Objects

Reachable

```text
Stack

student -----> Student Object
```

Unreachable

```text
Student Object
```

No reference.

GC can remove it.

---

# Generational Garbage Collection

The Heap is divided into generations.

```text
Heap

---------------------
Young Generation
---------------------

Eden

Survivor 1

Survivor 2

---------------------
Old Generation
---------------------
```

---

## Young Generation

Every new object starts here.

Specifically inside **Eden Space**.

```java
Student s = new Student();
```

↓

Created in Eden.

---

## Old Generation

If an object survives multiple Garbage Collection cycles,

Java moves it to

**Old Generation**.

Example

```text
Database Connection Pool

Spring Bean

Cache
```

These objects usually live for a long time.

---

# Minor GC

Runs on

Young Generation.

Fast.

---

# Major (Full) GC

Runs on

Old Generation.

Slower.

Can pause the application longer.

---

# Memory Leak in Java

Many people think Java has no Memory Leaks.

Wrong.

Java **can** have Memory Leaks.

The difference is:

The GC only removes **unreachable** objects.

If an object is still referenced,

the GC cannot remove it.

---

Example

```java
static List<Student> students = new ArrayList<>();

students.add(new Student());
```

Even if you never use that object again,

it is still inside the List.

The GC sees a reference.

So it cannot delete it.

This is a Memory Leak.

# Common Interview Questions

---

## 1. What is the difference between Stack and Heap?

**Answer**

> Stack stores method calls, local variables, and object references. Each thread has its own stack. Heap stores all objects and is shared among all threads. Stack memory is automatically released when methods finish, while Heap memory is managed by the Garbage Collector.

---

## 2. Where are Objects stored?

**Answer**

Objects are stored in the **Heap**.

References are usually stored in the **Stack**.

---

## 3. Can Stack store Objects?

**Answer**

No.

The Stack stores references.

The actual objects live in the Heap.

---

## 4. How does Garbage Collection work?

**Answer**

The Garbage Collector periodically scans the Heap.

If an object has no reachable references, it becomes eligible for collection and its memory can be reclaimed.

---

## 5. Does `System.gc()` force Garbage Collection?

**Answer**

No.

It only **requests** the JVM to perform Garbage Collection.

The JVM may ignore the request.

---

## 6. Can Java have Memory Leaks?

**Answer**

Yes.

If an object is still referenced but no longer needed, the GC cannot remove it.

---

## 7. What is the difference between Minor GC and Major GC?

|Minor GC|Major GC|
|---|---|
|Young Generation|Old Generation|
|Faster|Slower|
|Happens more frequently|Happens less frequently|

---

## 8. Why is Stack faster than Heap?

**Answer**

Because Stack memory is managed using simple push/pop operations, while Heap memory requires dynamic allocation and Garbage Collection.

# Tracing Question

```java
public class Test {

    public static void main(String[] args) {

        method1();

    }

    static void method1() {

        int x = 10;

        method2();

    }

    static void method2() {

        int y = 20;

        System.out.println(x + y);

    }

}
```

### What happens?

**Answer**

This code **does not compile**.

Error:

```
Cannot find symbol: x
```

Reason:

`x` is a **local variable** inside `method1()`.

Each method has its own **Stack Frame**.

Local variables are visible **only within their own method**.

`method2()` cannot access the local variables of `method1()`.

---

# Golden Interview Answer (30 seconds)

> **In Java, memory is mainly divided into Stack and Heap. Each thread has its own Stack, which stores method calls, local variables, and object references. The Heap is shared among all threads and stores all objects. The JVM automatically manages Heap memory using the Garbage Collector, which removes objects that are no longer reachable. New objects are created in the Young Generation (Eden Space), and long-lived objects are promoted to the Old Generation. Although Java has automatic Garbage Collection, memory leaks can still occur if unnecessary references prevent objects from becoming eligible for collection.**

# 2. Design Patterns (Singleton, Factory, Builder, Strategy)

These four patterns are among the **most frequently asked design patterns** in Java Backend and Spring Boot interviews because Spring itself uses them extensively.

## Singleton Pattern

### Definition

The **Singleton Pattern** ensures that **only one instance** of a class exists throughout the application's lifetime and provides a global access point to that instance.

### Example

```java
public class Singleton {

    private static Singleton instance;

    private Singleton() {}

    public static Singleton getInstance() {

        if (instance == null) {
            instance = new Singleton();
        }

        return instance;
    }
}
```

Usage:

```java
Singleton s1 = Singleton.getInstance();
Singleton s2 = Singleton.getInstance();

System.out.println(s1 == s2);
```

Output

```
true
```

Both variables point to the same object.

---

### Problem

This implementation is **not thread-safe**.

If two threads execute `getInstance()` simultaneously, both may see `instance == null` and each create a new object.

---

### Thread-safe Singleton

Common approaches:

- Enum Singleton (recommended)
    
- Double-Checked Locking with `volatile`
    
- Spring Singleton Beans (default scope)
    

---

### Where is Singleton used?

- Spring Beans (`@Component`, `@Service`)
    
- Logger
    
- Configuration classes
    
- Cache managers
    

---

## Factory Pattern

### Definition

The **Factory Pattern** creates objects without exposing the object creation logic to the client.

Instead of

```java
new Car();
```

you do

```java
VehicleFactory.createVehicle("car");
```

The factory decides which object to create.

---

### Why use Factory?

- Loose coupling
    
- Easier maintenance
    
- Easier to add new implementations
    

---

### Spring Example

```java
ApplicationContext.getBean(UserService.class);
```

Spring creates the object instead of you.

---

## Builder Pattern

### Definition

The Builder Pattern constructs complex objects **step by step**.

Instead of a constructor with many parameters,

```java
User user = new User(
    "Ali",
    "Cairo",
    23,
    "Backend",
    true,
    ...
);
```

Use

```java
User user = User.builder()
        .name("Ali")
        .age(23)
        .city("Cairo")
        .build();
```

---

### Benefits

- Readable code
    
- Supports optional fields
    
- Avoids the Telescoping Constructor problem
    
- Creates immutable objects easily
    

---

### Spring Example

Lombok

```java
@Builder
```

---

## Strategy Pattern

### Definition

The Strategy Pattern defines multiple algorithms and allows switching between them at runtime.

Example:

Payment System

Strategies:

- Credit Card
    
- PayPal
    
- Apple Pay
    

Each payment method implements the same interface.

```java
payment.pay();
```

The application chooses the strategy dynamically.

---

### Benefits

- Open/Closed Principle
    
- Easy to extend
    
- No huge `if-else` blocks
    

---

### Spring Example

Multiple implementations of the same interface injected based on business logic.

---

# Common Design Pattern Interview Questions

### Why is Singleton not thread-safe?

Because two threads may create two different instances simultaneously if no synchronization is used.

---

### When should you use Builder?

When an object has many optional parameters or complex construction logic.

---

### Factory vs Builder?

- **Factory** → Focuses on **creating** the appropriate object.
    
- **Builder** → Focuses on **constructing** one complex object step by step.
    

---

### Factory vs Strategy?

- **Factory** answers: **Which object should I create?**
    
- **Strategy** answers: **Which algorithm should I execute?**
    

---

### Why does Spring use Singleton by default?

Because services, repositories, and configuration classes are typically stateless. Reusing a single instance reduces memory usage and improves performance.

---

## Golden Interview Answer (30 seconds)

> **Singleton ensures only one instance of a class exists. Factory encapsulates object creation logic and hides the `new` keyword from clients. Builder constructs complex objects step by step and is ideal for classes with many optional parameters. Strategy encapsulates interchangeable algorithms and allows selecting the appropriate behavior at runtime. Spring Boot uses these patterns extensively—for example, Spring Beans are Singleton by default, `ApplicationContext` acts as a Factory, Lombok provides the Builder pattern through `@Builder`, and multiple implementations of the same interface are often used as Strategies.**
