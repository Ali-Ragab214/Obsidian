## مثال اقتصادي مهم

الوثيقة بتستخدم المثال التالي:

- 300 عضو.
    
- متوسط الاشتراك 700 جنيه.
    
- Churn شهري 8%.
    

بالتالي:

\[ 300 \times 0.08 = 24 \]

يعني 24 عضو مش بيجددوا شهريًا.

قيمة الاشتراكات المفقودة:

\[ 24 \times 700 = 16,800 \]

لو Kammel ساهم في تقليل الـ Churn من 8% إلى 6%، ده معناه 6 أعضاء إضافيين بيجددوا.

\[ 6 \times 700 = 4,200 \]

وده إيراد تجديدات إضافي في الشهر، بافتراض ثبات باقي العوامل.

وده مثال قوي جدًا في البيع.

بس خلي بالك: ده مش معناه إن كل الـ 4,200 جنيه Profit، ولا إن النظام هو السبب تلقائيًا. لازم تثبت إن التدخل بتاعك هو اللي ساهم في رجوع الأعضاء.

## A. Modular Monolith

اختيار ممتاز

أنا مؤيد جدًا للـ Modular Monolith بدل Microservices.

ليه؟

لأنك غالبًا هتشتغل بمفردك، ومش محتاج تضيف Distributed Systems Complexity من البداية.

لكن في نفس الوقت، مش عايز المشروع يبقى Package واحدة ضخمة.

الوثيقة بتقترح تقسيم المشروع إلى Modules:

```
com.kammel
│
├── identity
├── tenancy
├── members
├── plans
├── subscriptions
├── payments
├── checkin
├── notifications
├── risk
├── reporting
├── audit
│
└── common
```

أنا أفضل إن كل Module يكون له boundaries واضحة، وموديول Payments مثلًا ميستخدمش Repository الخاص بـ Members مباشرة.

يتعامل مع Public Service Interface أو Application API خاصة بالموديول.

استخدم Spring Modulith لاختبار الحدود دي، لكن مش لازم تحوّل كل حاجة إلى Framework abstractions زيادة عن الحاجة.

## B. Multi-tenancy

ميزة قوية جدًا للـ CV

دي من أهم القرارات المعمارية في المشروع كله.

افترض إن عندك:

- Gym A.
    
- Gym B.
    
- Gym C.
    

كل جيم عنده Members وPayments وSubscriptions خاصة بيه.

السؤال:

إزاي تضمن إن Gym A مستحيل يشوف بيانات Gym B؟

الحل المقترح في الوثيقة:

- `org_id` في الجداول.
    
- Tenant Context مستخرج من JWT.
    
- Hibernate Tenant Filter أو `@TenantId` عند ملاءمته.
    
- PostgreSQL Row-Level Security.
    
- Automated Integration Tests لمنع Data Leakage.
    

مثال:

```
CREATE POLICY tenant_isolation
ON members
USING (
    org_id = current_setting('app.current_org')::uuid
);
```

الفكرة إن حتى لو Developer نسي يضيف:

```
WHERE org_id = ?
```

قاعدة البيانات نفسها تمنع قراءة صفوف Tenant تاني.

لكن هنا عندي تحذير هندسي مهم:

RLS مش مجرد كتابة Policy وخلاص.

لازم تراعي:

1. استخدام `SET LOCAL` أو إعداد Transaction-scoped آمن للـ Tenant Context.
    
2. عدم استخدام Database Role يتجاوز RLS بدون قصد.
    
3. مراجعة `FORCE ROW LEVEL SECURITY` حسب صلاحيات الـ DB owner.
    
4. اختبار Connection Pooling عشان Tenant Context ما يتسربش بين Requests.
    
5. اختبار Background Jobs، لأنها مش بتيجي من HTTP Request عنده JWT.
    

ودي نقطة ممتازة جدًا تتكلم عنها في Interviews لو نفذتها فعلًا.

وتغيره في أي مكان.

أنت عندك Business Rules بتحكم الانتقالات.

مثلًا:

```
PENDING_PAYMENT
       |
       v
     ACTIVE
       |
       +------> FROZEN
       |          |
       |          v
       |        ACTIVE
       |
       v
  EXPIRING_SOON
       |
       v
     GRACE
       |
       v
    EXPIRED
```

والأحداث ممكن تكون:

- SubscriptionCreated.
    
- PaymentReceived.
    
- SubscriptionRenewed.
    
- SubscriptionFrozen.
    
- SubscriptionUnfrozen.
    
- SubscriptionExpired.
    

وهنا عايز أوضح فرق مهم:

وجود Subscription Events لا يعني بالضرورة إنك بتطبق Event Sourcing كامل.

ممكن تستخدم Event Records كـ Audit / Domain History، وتحتفظ بالـ Current State في Subscription Entity.

وده أبسط وأنسب للمشروع.

## D. Payments & Idempotency

دي نقطة لازم تنفذها باهتمام.

تخيل إن العميل ضغط زرار الدفع مرتين بسبب بطء الإنترنت.

أو Webhook وصل مرتين من Payment Provider.

إزاي تمنع تسجيل نفس الدفع مرتين؟

هنا تستخدم Idempotency Key مع Unique Constraint، وتنفذ التسجيل داخل Transaction.

مثلًا:

```
POST /api/payments
Idempotency-Key: abc-123
```

أول Request يسجل الدفعة.

ثاني Request بنفس المفتاح يرجع نفس النتيجة بدل تسجيل دفعة جديدة.

وده موضوع Production Engineering حقيقي.

2. المبالغ المالية تتخزن كـ Integer بالقروش أو `BigDecimal`، مش `double`.
    

0-doc.md

لكن فيه شوية إضافات أنصح بيها:

- Subscription Renewal History أو ربط واضح بين الاشتراكات القديمة والجديدة.
