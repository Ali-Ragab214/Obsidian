## 1. Java & Spring Boot Conventions

### 1.1 Java Version & Language Features
- **Java 21 (LTS):** Modern language features are encouraged:
  - Pattern matching for `switch` and `instanceof`.
  - Records for immutable data structures (DTOs, domain events, query projections).
  - Text blocks (`"""`) for complex SQL, prompts, or test payloads.
  - Virtual Threads (`Project Loom`) enabled in `application.yml` (`spring.threads.virtual.enabled: true`) for high-concurrency I/O.

### 1.2 Package & Class Naming Standards

```
com.kammel.{feature}.{layer}
```

| Component | Naming Pattern | Example |
|---|---|---|
| **Controller** | `{Feature}Controller` | `SubscriptionController` |
| **Service Interface** | `{Feature}Service` | `SubscriptionService` |
| **Service Implementation** | `{Feature}ServiceImpl` | `SubscriptionServiceImpl` |
| **Repository** | `{Feature}Repository` | `SubscriptionRepository` |
| **JPA Entity** | `{Entity}` (Singular) | `Subscription`, `CheckIn` |
| **Request DTO** | `{Action}{Entity}Request` | `CreateSubscriptionRequest`, `FreezeSubscriptionRequest` |
| **Response DTO** | `{Entity}Response` / `{Entity}SummaryResponse` | `SubscriptionResponse` |
| **Mapper** | `{Entity}Mapper` | `SubscriptionMapper` |
| **Exception** | `{Problem}Exception` | `InvalidStateTransitionException` |

### 1.3 Service Interfaces vs. Concrete Implementations
Avoid creating interfaces blindly. In Kammel:
1. **Public Module Boundaries Require Interfaces:** Every module exposes a clean public Java interface (`MemberService`, `SubscriptionService`) representing the contract other modules can safely invoke.
2. **Internal Module Helpers Do Not Require Interfaces:** Internal helper classes, validators, or private utilities within a module must be concrete classes. Do not create an interface if there is only ever one implementation that is internal to that module.

## 2. Dependency Injection & Clean Architecture

### 2.1 Constructor Injection Exclusively
- **Field injection (`@Autowired` on fields) is strictly prohibited.** Field injection prevents immutability, makes unit testing without reflection cumbersome, and hides circular dependencies.
- **Rule:** Use Lombok's `@RequiredArgsConstructor` or explicit constructor injection on all components:

```java
@Service
@RequiredArgsConstructor
public class PaymentServiceImpl implements PaymentService {

    private final PaymentRepository paymentRepository;
    private final SubscriptionService subscriptionService;
    private final ApplicationEventPublisher eventPublisher;
    // Fields are marked final for immutability
}
```

## 3. Lombok Usage Guidelines

Lombok reduces boilerplate, but improper usage causes critical JPA and Hibernate defects (such as infinite recursion, broken `hashCode`, and unintentional lazy initialization).

| Annotation | Policy | Rationale |
|---|---|---|
| `@Getter` / `@Setter` | ✅ **Approved** | Clean property access. |
| `@RequiredArgsConstructor` | ✅ **Approved** | Preferred constructor dependency injection. |
| `@Builder` | ✅ **Approved** | Excellent for DTOs and test fixtures. |
| `@Slf4j` | ✅ **Approved** | Standardized SLF4J logger injection. |
| `@ToString` | ⚠️ **Use with Care** | Explicitly exclude bidirectional JPA relationships: `@ToString.Exclude`. |
| `@EqualsAndHashCode` | ⚠️ **Restricted** | Never use default `@EqualsAndHashCode` on JPA entities. Base entity equality on UUID or natural business key, never generated DB sequence IDs. |
| `@Data` | ❌ **PROHIBITED on JPA Entities** | Combines `@ToString`, `@EqualsAndHashCode`, and getters/setters, causing broken lazy collections and performance bugs. Allowed on DTOs only. |

## 4. Entity Design & JPA Best Practices

1. **Explicit Table & Column Names:** Always provide `@Table(name = "...")` and `@Column(name = "...")` using `snake_case` database naming.
2. **UUID Primary Keys:** Use `UUID` generated by PostgreSQL (`@GeneratedValue(strategy = GenerationType.UUID)`).
3. **No Bidirectional `@OneToMany` unless Justified:** Prefer unidirectional relationships or query-based lookups to avoid accidental loading of massive collections.
4. **Always Set FetchType.LAZY:** All `@ManyToOne` and `@OneToOne` associations must explicitly specify `fetch = FetchType.LAZY`. (Hibernate default is `EAGER`, causing severe N+1 query storms).
5. **Audit Columns:** All mutable entities must extend `BaseAuditableEntity` providing `createdAt`, `updatedAt`, and `createdBy`.

## 5. Transaction & Consistency Boundaries

1. **Service Layer Owns Transactions:** Apply `@Transactional` exclusively to service implementation methods. Controllers and Repositories must never declare `@Transactional`.
2. **Explicit Read-Only Transactions:** All query methods must declare `@Transactional(readOnly = true)`. This enables Hibernate performance optimizations (disabling dirty checking and flushing).
3. **Short Transactions:** Keep transaction boundaries as tight as possible. Never invoke external network I/O (e.g., sending emails, WhatsApp APIs, third-party webhooks) inside an active database transaction.

## 6. Logging, Security & PII Protection

1. **No Personal Identifiable Information (PII) in Logs:**
   - **Never log:** Member phone numbers, national IDs, credit card details, or full customer names in application logs.
   - **Approved:** Log entity UUIDs, HTTP status codes, execution durations, and error root causes.
2. **SLF4J Parameterized Logging:** Use parameterized placeholders; never string concatenation:
   ```java
   // Correct:
   log.info("Subscription {} successfully activated for tenant {}", subId, orgId);
   // Prohibited:
   log.info("Subscription " + subId + " for " + memberName);
   ```
3. **MDC (Mapped Diagnostic Context) Tracing:** A servlet filter injects `correlationId`, `orgId`, and `userId` into SLF4J MDC, ensuring every log line across the request lifecycle includes tenant context for debugging.

## 7. Git Workflow & Commit Standards

### 7.1 Branching Model
- `main`: Production-ready code; tagged with releases.
- `develop`: Integration branch for completed features.
- `feature/{epic}-{task-id}-{short-description}`: Feature branches (e.g., `feature/sub-002-state-machine`).
- `bugfix/{issue-id}-{short-description}`: Bugfix branches.

### 7.2 Conventional Commits
All commit messages must adhere to the Conventional Commits specification:
```
<type>(<scope>): <short imperative description>

[optional body explaining WHY, not WHAT]

[optional footer referencing task ID]
```

- **Types:**
  - `feat`: A new user-facing business feature.
  - `fix`: A bug fix.
  - `refactor`: Code change that neither fixes a bug nor adds a feature.
  - `test`: Adding or correcting tests.
  - `docs`: Documentation changes only.
  - `chore`: Build tasks, package upgrades, Docker configs.
- **Example:**
  ```
  feat(subscriptions): implement state transition to grace on expiration

  When an active subscription reaches end_date and the plan has grace_days > 0,
  transition state to GRACE and record SubscriptionEvent.

  Closes TSK-SUB-002
  ```

## 8. Code Review & Pull Request Quality Checklist

Before opening or merging any Pull Request into `develop` or `main`:

- [ ] **Multi-Tenancy:** Does every new JPA entity contain `org_id`? Does the Flyway migration include RLS policy configuration?
- [ ] **Financial Safety:** Are all financial computations performed using `Long` piasters? Are floating-point types completely absent?
- [ ] **Authorization:** Are all new service methods protected with explicit `@PreAuthorize` annotations?
- [ ] **Testing:** Is there unit test coverage for domain rules and integration test coverage for tenant isolation?
- [ ] **DTO Encapsulation:** Are JPA entities prevented from leaking into controller inputs or outputs?
- [ ] **Logging & Privacy:** Is the PR free of raw member phone numbers or PII in log statements?
- [ ] **Database Performance:** Are all new foreign keys and search query columns backed by composite tenant indexes?
