# Q1 — الفرق بين `@Injectable()` و `@Inject()`

### 🔹 `@Injectable()`

يتحط فوق الـ **class** نفسه.

معناه إن Nest يسمح للكلاس ده يدخل الـ IoC Container ويكون قابل للحقن (Injection).

بدونه ➜ Nest مش هيعرف ينشئ instance منه.

```ts
@Injectable()
export class UserService {}
```

💡 تخيلها كأنك بتقول لـ Nest:  
"الكلاس ده Provider — دخّله جوه الـ Container."

---

### 🔹 `@Inject()`

يتحط على **constructor parameter**.

نستخدمه لما Nest **مش قادر يعرف dependency من النوع (type)** لوحده.

حالات استخدامه:

- Injection باستخدام string token
    
- Injection باستخدام symbol
    
- Custom providers
    

```ts
@Injectable()
export class UserService {
  constructor(
    private userRepo: UserRepository, // Nest عرفه من النوع تلقائياً

    @Inject('CONFIG')                 // لازم Inject لأن ده string مش type
    private config: AppConfig,
  ) {}
}
```

### 💡 الخلاصة

|Decorator|مكانه|وظيفته|
|---|---|---|
|`@Injectable()`|على الـ class|يسمح بإدارة الكلاس داخل IoC container|
|`@Inject()`|على constructor parameter|يحدد dependency لما النوع مش كفاية|

# Q2 — Provider Scopes

الـ Scope = عمر الـ Provider داخل التطبيق.

---

## 1️⃣ Default Scope (Singleton)

```ts
@Injectable()
export class UserService {}
```

- Instance واحدة فقط طول عمر التطبيق.
    
- 99% من الـ providers لازم تكون كده.
    

📌 تستخدمه في:

- Services
    
- Repositories
    
- Database connections
    

---

## 2️⃣ Request Scope

```ts
@Injectable({ scope: Scope.REQUEST })
export class RequestContextService {}
```

- Instance جديدة **لكل HTTP request**.
    
- مفيد لو محتاج بيانات الـ request داخل service.
    

مثال:

- user الحالي
    
- request id
    
- logging لكل request
    

---

## 3️⃣ Transient Scope

```ts
@Injectable({ scope: Scope.TRANSIENT })
export class LoggerService {}
```

- Instance جديدة **كل مرة يتم Inject فيها**.
    

نادراً جداً تستخدمه.

---

### ⚠️ معلومة Interview مهمة — Scope Bubbling

لو Service Singleton اعتمدت على Request scoped provider ➜ تتحول تلقائياً لـ Request scope.

# Q3 — `exports` في Modules

الـ Module هو Container صغير خاص بيه.

الـ Provider جوه module **مش متاح برّه** إلا لو عملت export.

---

## مثال عملي

### UserModule

```ts
@Module({
  providers: [UserService],
  exports: [UserService],
})
export class UserModule {}
```

### OrderModule

```ts
@Module({
  imports: [UserModule],
})
export class OrderModule {}
```

دلوقتي `OrderService` يقدر يحقن `UserService`.

---

### ⚠️ أشهر Error في Nest

```
Nest can't resolve dependencies
```

غالباً سببه إنك نسيت `exports`.

# Q4 — Custom Providers (مهم جداً)

---

## useClass — تبديل Implementation

نستخدمه لما يكون عندنا **interfaces أو multiple implementations**

```ts
{
  provide: PaymentService,
  useClass: StripePaymentService,
}
```

مفيد في:

- testing (mock service)
    
- environments مختلفة
    

---

## useValue — قيمة جاهزة

```ts
{
  provide: 'JWT_SECRET',
  useValue: process.env.JWT_SECRET,
}
```

نستخدمه مع:

- config values
    
- constants
    

---

## useFactory — إنشاء ديناميكي أو Async

```ts
{
  provide: 'DB_CONNECTION',
  useFactory: async (config: ConfigService) => {
    return mongoose.connect(config.get('DB_URL'));
  },
  inject: [ConfigService],
}
```

نستخدمه لما:

- في logic أثناء الإنشاء
    
- محتاج async
    
- محتاج inject dependencies
    

---

### 💡 قاعدة حفظ سريعة

|الحالة|نستخدم|
|---|---|
|قيمة ثابتة|useValue|
|logic أو async|useFactory|
|تبديل implementation|useClass|

# Q5 — Circular Dependency و `forwardRef`

يحصل لما Service يعتمد على Service تاني والعكس.

```
UserService → PostService
PostService → UserService
```

Nest مش يعرف يحدد مين يبدأ الأول.

---

## الحل

```ts
@Injectable()
export class UserService {
  constructor(
    @Inject(forwardRef(() => PostService))
    private postService: PostService,
  ) {}
}
```

💡 نصيحة إنترفيو مهمة:

> وجود circular dependency غالباً علامة إن التصميم محتاج refactor.

الحل الأفضل:

- استخراج shared logic في service ثالث.

# Q6 — إزاي Nest يعرف Dependencies تلقائياً؟

السحر اسمه:

## TypeScript Reflection Metadata

عند كتابة:

```ts
constructor(private repo: UserRepository) {}
```

TypeScript يخزن metadata مخفية في الكود:

```
design:paramtypes → [UserRepository]
```

Nest يقرأها باستخدام:

```ts
Reflect.getMetadata()
```

وبعدين:

- يجيب UserRepository من الـ Container
    
- يحقنه في UserService
    

---

### ⚠️ لذلك هذا الإعداد إجباري

`tsconfig.json`

```json
"emitDecoratorMetadata": true,
"experimentalDecorators": true
```

بدونهم DI لن يعمل.

# Q7 — Global Modules vs Imports

---

## Module عادي

كل Module محتاج يعمل import بنفسه.

```ts
@Module({
  providers: [UserService],
  exports: [UserService],
})
export class UserModule {}
```

---

## Global Module

```ts
@Global()
@Module({
  providers: [ConfigService],
  exports: [ConfigService],
})
export class ConfigModule {}
```

يتم تسجيله مرة واحدة ويصبح متاح في كل التطبيق.

---

### متى نستخدم Global؟

✔ ConfigService  
✔ Logger  
✔ Auth helpers

### متى نتجنبه؟

في أغلب الحالات — لأن explicit imports أوضح وأسهل debugging.

# 🧠 Full Application Flow

ده أهم جزء لازم تبقى فاهمه كويس:

```
nest start
   ↓
Nest يقرأ AppModule
   ↓
يعمل scan لكل modules و providers
   ↓
يبني Dependency Graph كامل
   ↓
ينشئ كل providers (Singletons)
   ↓
يحفظهم داخل IoC Container
   ↓
يصل request
   ↓
Nest يجلب Controller جاهز بالـ dependencies
   ↓
Controller → Service → Repository → DB
   ↓
Response
```
