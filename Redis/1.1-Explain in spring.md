## أولًا: كيف Spring Cache بيشتغل؟

افترض عندك:

```java
public Course getCourse(Long id) {
    return courseRepository.findById(id)
            .orElseThrow();
}
```

كل مرة الميثود دي تتنادى:

1. Request
    
2. Service
    
3. Database
    
4. Return Result
    

لكن مع Cache:

```java
@Cacheable("courses")
public Course getCourse(Long id) {
    return courseRepository.findById(id)
            .orElseThrow();
}
```

الفلو بيبقى:

```
Request
   |
Cache ?
   |
   |---- موجود --> رجع البيانات
   |
   |---- مش موجود
              |
           Database
              |
         Save in Cache
              |
           Return
```

# 1) @Cacheable


# هم Properties في @Cacheable

| Property   | وظيفتها             |
| ---------- | ------------------- |
| value      | اسم الـ Cache       |
| cacheNames | نفس value           |
| key        | تخصيص المفتاح       |
| condition  | شرط قبل الـ Cache   |
| unless     | شرط بعد النتيجة     |
| sync       | يمنع Cache Stampede |

أشهر Annotation.

```java
@Cacheable("courses")
public Course getCourse(Long id) {
    return courseRepository.findById(id)
            .orElseThrow();
}
```

معناها:

> لو البيانات موجودة في Cache رجعها ومتنفذش الميثود.

## Custom Key

```java
@Cacheable(
    value = "courses",
    key = "#id"
)

@Cacheable(
value="courses",
key="#id"
)
```

نفس النتيجة.

---

مثال أكثر تعقيدًا:

```java
@Cacheable(
    value = "courses",
    key = "#course.id"
)

@Cacheable(
value="courses",
key ="#course.id"
)
```

```java
public Course find(Course course)
```

هياخد:

```java
course.getId()
```

كـ Key.

## Multiple Parameters

```java
@Cacheable(
    value = "courses",
    key = "#id + '-' + #name"
)

```

لو:

```java
get(1,"java")
```

يبقى:

```
courses::1-java
```

# condition

تشغل Cache بشروط.

```java
@Cacheable(
    value = "courses",
    condition = "#id > 10"
)

@Cacheable(
value="courses",
condition ="#id > 10"
)

@Cacheable(
value="courses",
condition="#id > 10"
)
```

لو:

```java
getCourse(5)
```

مش هيعمل Cache.

---

لو:

```java
getCourse(20)
```

هيعمل Cache.

# unless

العكس تقريبًا.

بيتفحص بعد تنفيذ الميثود.

```java
@Cacheable(
    value = "courses",
    unless = "#result == null"
)
```

لو النتيجة:

```java
null
```

مش يحفظها.

---

مثال:

```java
@Cacheable(
    value = "courses",
    unless = "#result.price < 100"
)
لو الشرط دا اتحقق متكيشش الحاجه دي 
```

لو الكورس سعره أقل من 100:

مش يتحفظ.

# 2) @CachePut

ناس كتير بتتلخبط بينها وبين Cacheable.

---

## Cacheable

لو موجود Cache:

```
مش ينفذ الميثود
```

---

## CachePut

```
ينفذ الميثود دائمًا
ويحدث Cache دائمًا
```

---

مثال:

```java
@CachePut(
    value = "courses",
    key = "#course.id"
)
public Course updateCourse(Course course){
    return repository.save(course);
}
```

الفلو:

```
Update DB

↓

Update Cache

↓

Return
```

---

بعد التحديث:

```
courses::1
```

يتحدث تلقائيًا.

# 3) @CacheEvict

لحذف بيانات من Cache.

---

مثال:

```java
@CacheEvict(
    value = "courses",
    key = "#id"
)
public void deleteCourse(Long id){
    repository.deleteById(id);
}
```

بعد الحذف:

```
courses::1
```

تتمسح.

---

# allEntries

```java
@CacheEvict(
    value = "courses",
    allEntries = true
)
```

يمسح:

```
courses::*
```

كل الكاش.

---

مثال:

```java
@CacheEvict(
    value = "courses",
    allEntries = true
)
public void clearCache() {}
```

---

# beforeInvocation

الافتراضي:

```java
beforeInvocation = false
```

يعني:

```
نفذ الميثود
ثم امسح الكاش
```

---

لو:

```java
@CacheEvict(
    value = "courses",
    key = "#id",
    beforeInvocation = true
)
```

يبقى:

```
امسح الكاش
ثم نفذ الميثود
```

حتى لو الميثود فشلت.

# 4) @Caching

لما تحتاج أكتر من Annotation.

مثال:

```java
@Caching(
        put = {
                @CachePut(
                        value = "courses",
                        key = "#course.id"
                )
        },
        evict = {
                @CacheEvict(
                        value = "courseList",
                        allEntries = true
                )
        }
)
```

معناه:

```
حدث Course Cache

+

امسح List Cache
```

# طب إزاي أخلي البيانات Updated دايمًا؟

عندك 3 طرق:

## 1) CachePut

بعد كل Update.

```java
@CachePut
```

---

## 2) CacheEvict

بعد Update.

```java
@CacheEvict
```

ثم أول Request يجيب بيانات جديدة من DB.

---

## 3) TTL (الأشهر مع Redis)

في Redis تحدد مدة صلاحية.

مثال:

```yaml
spring:
  cache:
    redis:
      time-to-live: 10m
```

أو:

```yaml
spring:
  cache:
    redis:
      time-to-live: 600000
```

بعد 10 دقائق:

```
Cache Expired
```

وأول Request بعدها يجيب من DB ويعيد التخزين.

# نقطة مهمة جدًا

الـ Cache Annotations شغالة بـ AOP.

يعني لو عندك:

```java
@Service
public class CourseService {

    @Cacheable("courses")
    public Course get(Long id){
        ...
    }

    public void test(){
        get(1L);
    }
}
```

هنا الكاش **لن يعمل**.

ليه؟

لأن:

```java
this.get(1L)
```

Internal Call.

لا يمر عبر Proxy الخاص بـ Spring.

لازم الميثود تتنادى من Bean خارجي.

# أكثر Setup شائع في المشاريع

```java
@Cacheable(key = "#id")
public CourseDTO getCourse(Long id)

@CachePut(key = "#course.id")
public CourseDTO updateCourse(CourseDTO course)

@CacheEvict(key = "#id")
public void deleteCourse(Long id)

@CacheEvict(allEntries = true)
public void clearAllCourses()
```

وده تقريبًا 90% من استخدام الـ Cache في مشاريع Spring Boot الحقيقية.

وأهم حاجة تركز عليها هي:

- `value / cacheNames`
    
- `key`
    
- `condition`
    
- `unless`
    
- `sync`
    
- `allEntries`
    
- `beforeInvocation`
    
- الفرق الجوهري بين `@Cacheable` و `@CachePut` و `@CacheEvict`
    

لو عايز بعد كده نشرح Redis Cache Manager Configuration نفسها (TTL لكل Cache بشكل مختلف، Serialization بـ Jackson، RedisCacheConfiguration، RedisTemplate، Cache Aside Pattern) فدي النقلة اللي بعدها واللي بتفرق فعلًا بين مشروع متدرب ومشروع Production.
