ممتاز. معظم الناس بتفهم `@Cacheable` لكن بتتلخبط في `@CachePut` لأنهم فاكرين إنها "نسخة تانية" من `@Cacheable`، بينما الحقيقة مختلفة تمامًا.

---

# الفكرة الأساسية

## Analogy

تخيل عندك:

```text
Database = الحقيقة
Redis = نسخة سريعة
```

عندك User:

```text
Ali
Age = 24
```

مخزن في Redis.

---

بعد شوية عمل Update:

```text
Ali
Age = 25
```

الـ DB اتحدثت.

لكن Redis لسه فيها:

```text
Age = 24
```

بقت البيانات قديمة (Stale Data).

هنا يجي دور `@CachePut`.

---

# تعريف @CachePut

`@CachePut`

### دائمًا

1. ينفذ الـ Method
    
2. يجيب النتيجة الجديدة
    
3. يحطها في الـ Cache
    

---

عكس `@Cacheable`.

---

# مقارنة مهمة جدًا

## @Cacheable

```java
@Cacheable("users")
public User getUser(Long id)
```

لو الـ Cache فيها User:

```text
Cache Hit
↓
يرجع من Redis
↓
ولا يدخل الميثود أصلاً
```

---

## @CachePut

```java
@CachePut("users")
public User updateUser(...)
```

```text
ينفذ الميثود كل مرة
↓
يحدث DB
↓
يحدث Cache
↓
يرجع النتيجة
```

---

# مثال عملي

## Get User

```java
@Cacheable(value = "users", key = "#id")
public User getUser(Long id) {

    System.out.println("Fetching User");

    return repository.findById(id)
            .orElseThrow();
}
```

---

## Update User

```java
@CachePut(value = "users", key = "#id")
public User updateUser(
        Long id,
        UpdateUserRequest request
) {

    User user = repository.findById(id)
            .orElseThrow();

    user.setName(request.name());

    return repository.save(user);
}
```

---

# الفلو

أول مرة:

```java
getUser(1L);
```

---

Redis:

```text
users::1
↓
{
   "id":1,
   "name":"Ali"
}
```

---

بعدها:

```java
updateUser(1L, "Ahmed");
```

---

اللي يحصل:

```text
DB Updated
↓
Cache Updated
↓
users::1
↓
{
   "id":1,
   "name":"Ahmed"
}
```

---

بعدها:

```java
getUser(1L);
```

---

هيرجع:

```text
Ahmed
```

من Redis مباشرة.

# مثال SkillHub

نفترض عندك Course.

---

## قراءة

```java
@Cacheable(
        value = "courses",
        key = "#id"
)
public CourseResponse getCourse(Long id) {

    return mapper.toResponse(
            repository.findById(id).orElseThrow()
    );
}
```

---

## تعديل

```java
@CachePut(
        value = "courses",
        key = "#id"
)
public CourseResponse updateCourse(
        Long id,
        UpdateCourseRequest request
) {

    Course course =
            repository.findById(id).orElseThrow();

    course.setTitle(request.title());

    repository.save(course);

    return mapper.toResponse(course);
}
```

---

بعد التعديل:

```text
Cache
↓
updated automatically
```

# important
# نقطة مهمة جدًا

الـ key لازم يبقى نفس Key المستخدم في @Cacheable.

---

مثال صحيح:

```java
@Cacheable(
        value = "users",
        key = "#id"
)
```

```java
@CachePut(
        value = "users",
        key = "#id"
)
```

---

مثال غلط:

```java
@Cacheable(
        value = "users",
        key = "#id"
)
```

```java
@CachePut(
        value = "users",
        key = "#result.email"
)
```

---

كده هتحدث Cache مختلفة أصلاً.

---

# استخدام #result

من أقوى الحاجات في `@CachePut`.

---

```java
@CachePut(
        value = "users",
        key = "#result.id"
)
public User save(User user) {

    return repository.save(user);
}
```

---

هنا Spring:

```text
ينفذ الميثود
↓
يستقبل النتيجة
↓
يقرأ result.id
↓
يحطها في Cache
```

---

# condition

تحديث الكاش بشرط.

```java
@CachePut(
        value = "users",
        key = "#id",
        condition = "#id > 100"
)
```

---

لو:

```java
updateUser(50L)
```

مش هيحدث الكاش.

---

# unless

بعد تنفيذ الميثود.

```java
@CachePut(
        value = "users",
        key = "#id",
        unless = "#result == null"
)
```

---

لو رجع:

```java
null
```

مش هيخزن حاجة.

# إمتى أستخدم CacheEvict بدل CachePut؟

لو عندك:

```java
updateCourse()
```

فيه اختيارين.

---

## الاختيار الأول

```java
@CachePut
```

يحدث الكاش فورًا.

---

## الاختيار الثاني

```java
@CacheEvict
```

يمسح الكاش.

---

بعدها أول Read:

```text
DB
↓
Cacheable
↓
Cache Again
```

---

# الفرق النهائي

|Annotation|هل الميثود تنفذ؟|هل يقرأ من Cache؟|هل يكتب في Cache؟|
|---|---|---|---|
|@Cacheable|أحيانًا|نعم|نعم|
|@CachePut|دائمًا|لا|نعم|
|@CacheEvict|دائمًا|لا|يمسح|

احفظ الجملة دي:

```text
@Cacheable
= اقرأ من الكاش لو موجود

@CachePut
= حدث الكاش بالقيمة الجديدة

@CacheEvict
= امسح الكاش
```

ولو فهمت `Cacheable + CachePut` كويس، يبقى الخطوة الطبيعية بعدها هي فهم `@CacheEvict` خصوصًا `allEntries=true` و `beforeInvocation=true` لأن دول أكتر نقطتين بيغلط فيهم المطورين في المشاريع الحقيقية.
