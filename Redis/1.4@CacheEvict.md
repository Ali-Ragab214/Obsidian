ممتاز. دلوقتي وصلنا لآخر ضلع في المثلث:

```text
@Cacheable
    ↓
Read

@CachePut
    ↓
Update Cache

@CacheEvict
    ↓
Remove Cache
```

---

# فكرة @CacheEvict

## Analogy

تخيل عندك في Redis:

```json
{
  "id": 1,
  "name": "Ali"
}
```

المستخدم اتمسح من الـ Database.

لكن Redis لسه فيها:

```json
{
  "id": 1,
  "name": "Ali"
}
```

بقى عندك Data غلط.

الحل؟

امسحها من الـ Cache.

وده بالضبط دور:

```java
@CacheEvict
```

---

# أول مثال

## قراءة

```java
@Cacheable(
        value = "users",
        key = "#id"
)
public User getUser(Long id) {

    return repository.findById(id)
            .orElseThrow();
}
```

---

## حذف

```java
@CacheEvict(
        value = "users",
        key = "#id"
)
public void deleteUser(Long id) {

    repository.deleteById(id);
}
```

---

# الفلو

قبل الحذف:

```text
Redis

users::1
↓
Ali
```

---

تشغيل:

```java
deleteUser(1L);
```

---

بعدها:

```text
users::1
↓
Deleted
```

الكاش اتمسحت.

---

# لو معملتش CacheEvict

هيحصل:

```text
DB
↓
User Deleted

Redis
↓
Still Exists
```

وتبدأ تظهر مشاكل غريبة.

---

# allEntries = true

دي من أهم الحاجات.

---

عندك:

```text
courses::1
courses::2
courses::3
courses::4
```

---

عايز تمسحهم كلهم.

بدل:

```java
@CacheEvict(
        value = "courses",
        key = "#id"
)
```

استخدم:

```java
@CacheEvict(
        value = "courses",
        allEntries = true
)
```

---

هيحصل:

```text
courses::*
↓
Deleted
```

---

# إمتى أستخدم allEntries؟

مثال:

```java
getAllCourses()
```

---

متخزنة:

```java
@Cacheable("courses")
public List<Course> getAllCourses() {
    ...
}
```

---

لما تعمل:

```java
createCourse()
```

أو:

```java
updateCourse()
```

القائمة كلها بقت قديمة.

---

ساعتها:

```java
@CacheEvict(
        value = "courses",
        allEntries = true
)
public Course createCourse(...) {
    ...
}
```

# beforeInvocation

دي نقطة Interview مشهورة جدًا.

---

الوضع الطبيعي:

```java
@CacheEvict(...)
```

معناه:

```text
Execute Method
↓
Success
↓
Delete Cache
```

---

مثال:

```java
@CacheEvict(
        value = "users",
        key = "#id"
)
public void deleteUser(Long id) {

    repository.deleteById(id);
}
```

---

لو حصل Exception:

```java
throw new RuntimeException();
```

---

الكاش مش هتتمسح.

وده غالبًا السلوك المطلوب.

---

# beforeInvocation = true

```java
@CacheEvict(
        value = "users",
        key = "#id",
        beforeInvocation = true
)
```

---

الفلو:

```text
Delete Cache
↓
Execute Method
↓
Even if Exception occurs
```

---

يعني الكاش هتتمسح مهما حصل.

---

## إمتى أستخدمها؟

نادر جدًا.

غالبًا:

```text
95%
beforeInvocation = false
```

(وهو الـ default).

---

# condition

تمسح بشرط.

```java
@CacheEvict(
        value = "users",
        key = "#id",
        condition = "#id > 100"
)
```

---

```java
deleteUser(50L);
```

❌ لا تمسح.

---

```java
deleteUser(200L);
```

✅ تمسح.

# CachePut ولا CacheEvict؟

دي أهم نقطة.

---

عندك:

```java
updateCourse()
```

---

## حل 1

```java
@CachePut
```

---

الفلو:

```text
Update DB
↓
Update Cache
```

---

ميزة:

```text
أسرع بعد التحديث
```

---

## حل 2

```java
@CacheEvict
```

---

الفلو:

```text
Update DB
↓
Delete Cache
```

---

أول Read بعدها:

```text
DB
↓
Cacheable
↓
Cache Again
```

---

ميزة:

```text
أبسط
```

# ملخص سريع جدًا

|Annotation|ماذا يفعل؟|
|---|---|
|`@Cacheable`|اقرأ من الكاش لو موجود|
|`@CachePut`|حدث الكاش بالقيمة الجديدة|
|`@CacheEvict`|امسح الكاش|

---

|Property|وظيفتها|
|---|---|
|`key`|تحديد الـ Cache Key|
|`allEntries=true`|مسح كل الـ Cache|
|`beforeInvocation=true`|امسح قبل تنفيذ الميثود|
|`condition`|امسح بشرط|

احفظ القاعدة الذهبية:

```text
GET
 ↓
@Cacheable

UPDATE
 ↓
@CachePut أو @CacheEvict

DELETE
 ↓
@CacheEvict
```

وده تقريبًا الـ Pattern اللي هتستخدمه في 90% من مشاريع Spring Boot + Redis.
