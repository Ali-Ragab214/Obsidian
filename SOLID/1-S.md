
---

# يعني ايه Single Responsibility ؟

النص الرسمي:

> A class should have only **one reason to change**

بالعربي 👇  
كل Class يكون مسؤول عن **حاجة واحدة بس**.

مش معنى كده يعمل وظيفة واحدة فقط…  
لا، يعمل مجموعة وظائف **لكن كلها تخص نفس المسؤولية**.

---

# يعني ايه “سبب واحد للتغيير” ؟

اسأل نفسك السؤال ده:

لو حصل تغيير في النظام…  
هل هعدّل الكلاس ده بسبب **أكتر من سبب مختلف؟**

لو الإجابة = نعم ❌  
يبقى الكلاس كسر SRP.

---

# مثال واقعي 👌

عندنا سيستم Users  
وكتبنا كلاس اسمه:

```java
class UserService {
    public void registerUser(String name, String email) {
        // save to database
        System.out.println("User saved to DB");
    }

    public void sendEmail(String email) {
        System.out.println("Email sent");
    }

    public void generateReport() {
        System.out.println("Report generated");
    }
}
```

الكود ده شكله بسيط… لكنه **غلط جداً**.

---

# ليه ده كسر SRP ؟ 💣

الكلاس ده فيه **3 مسؤوليات مختلفة**:

|الميثود|المسؤولية|
|---|---|
|registerUser|Database|
|sendEmail|Email service|
|generateReport|Reporting|

يعني الكلاس ده ممكن يتغير لو:

- غيرنا database 😐
    
- غيرنا email provider 😐
    
- غيرنا report format 😐
    

يبقى عنده **3 أسباب للتغيير** → كسر SRP ❌

---

# نطبّق SRP صح ✅

نفصل كل مسؤولية في كلاس لوحدها.

---

## 1️⃣ مسؤولية حفظ البيانات

```java
class UserRepository {
    public void saveUser(String name, String email) {
        System.out.println("User saved to DB");
    }
}
```

---

## 2️⃣ مسؤولية الإيميل

```java
class EmailService {
    public void sendEmail(String email) {
        System.out.println("Email sent");
    }
}
```

---

## 3️⃣ مسؤولية التقارير

```java
class ReportService {
    public void generateReport() {
        System.out.println("Report generated");
    }
}
```

---

## 4️⃣ الكلاس الأساسي يجمعهم فقط

```java
class UserService {

    private UserRepository userRepository = new UserRepository();
    private EmailService emailService = new EmailService();

    public void registerUser(String name, String email) {
        userRepository.saveUser(name, email);
        emailService.sendEmail(email);
    }
}
```

لاحظ الفرق 💡  
UserService بقى:

- ما بيعملش database بنفسه
    
- ما بيبعتش email بنفسه
    
- مجرد **Coordinator**
    

وده التصميم الصح.

---

# ليه SRP مهم جداً ؟

تخيل تغيير صغير:

لو غيرنا email provider من Gmail → SendGrid

قبل SRP:

- هنفتح UserService ونعدل فيه 💣
    

بعد SRP:

- هنعدل EmailService فقط 🎉
    

---

# مثال حياتي بسيط 🧠

تخيل موظف في شركة:

- محاسب
    
- HR
    
- IT
    
- Security
    

شخص واحد بيعمل كل حاجة 😵‍💫  
أكيد هيبوّظ الدنيا.

SRP بيقول:

> خلي كل شخص مسؤول عن دور واحد فقط.

---

# علامات إنك كاسر SRP 🚨

لو الكلاس:

- طويل جداً
    
- فيه services مختلفة
    
- فيه كلمات زي (Email / DB / PDF / API) مع بعض
    

يبقى بنسبة كبيرة كاسر SRP.

---

# الخلاصة السريعة 🏆

|غلط|صح|
|---|---|
|Class يعمل كل حاجة|كل مسؤولية في Class|
|أسباب تغيير كثيرة|سبب تغيير واحد|
|Coupling عالي|Code نظيف وسهل|

---
