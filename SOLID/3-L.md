# 3. L — Liskov Substitution Principle (LSP)

Interview Question: What is the Liskov Substitution Principle?

الإجابة النموذجية:

> Objects of a superclass should be replaceable with objects of its subclasses without breaking the correctness of the program.

بالمصري: لو عندي `Parent` class وعملت منها `Child` class، المفروض أقدر أستخدم الـ `Child` مكان الـ `Parent` من غير ما سلوك البرنامج يبوظ أو النتيجة تبقى غير متوقعة.

## 1. مثال غلط — Violation of LSP

تخيل إن عندنا `Bird` class، وكل الطيور بتطير حسب التصميم بتاعنا.

```
class Bird {
    public void fly() {
        System.out.println("Bird is flying");
    }
}

class Sparrow extends Bird {
    @Override
    public void fly() {
        System.out.println("Sparrow is flying");
    }
}

class Penguin extends Bird {
    @Override
    public void fly() {
        throw new UnsupportedOperationException(
            "Penguins cannot fly!"
        );
    }
}
```

دلوقتي عندنا method بتتعامل مع أي `Bird`:

```
public void makeBirdFly(Bird bird) {
    bird.fly();
}
```

نجرب:

```
makeBirdFly(new Sparrow()); // Works fine

makeBirdFly(new Penguin()); // Throws exception!
```

إيه المشكلة؟

الـ `makeBirdFly()` متوقعة إن أي `Bird` تقدر تطير، لكن لما نبعتلها `Penguin` البرنامج بيقع في Exception.

إذًا الـ `Penguin` مش قابلة للاستبدال بـ `Bird` في السياق ده، وده انتهاك لمبدأ LSP.

خلي بالك: المشكلة مش إن الـ Penguin مش بتطير في الحقيقة؛ المشكلة إننا صممنا الـ inheritance بشكل بيقدم contract غير صحيح.

## 2. الحل الصح — Following LSP

بدل ما نخلي كل الطيور لازم تطير، نفصل القدرة على الطيران في interface مستقلة.

Bird

الخصائص المشتركة للطيور

Sparrow

implements Flyable

Penguin

Does not implement Flyable

الكود:

```
interface Bird {
    void eat();
}

interface Flyable {
    void fly();
}

class Sparrow implements Bird, Flyable {

    @Override
    public void eat() {
        System.out.println("Sparrow is eating");
    }

    @Override
    public void fly() {
        System.out.println("Sparrow is flying");
    }
}

class Penguin implements Bird {

    @Override
    public void eat() {
        System.out.println("Penguin is eating");
    }
}
```

كده:

- `Sparrow` تقدر تتعامل معاها كـ `Bird` أو `Flyable`.
    
- `Penguin` تقدر تتعامل معاها كـ `Bird` من غير ما نطلب منها سلوك مش بتدعمه.
    
- أي method بتستقبل `Bird` وتطلب منها `eat()` تقدر تستقبل النوعين من غير ما التصميم يفرض عليهم سلوك غير مناسب.
    

وده تصميم أفضل بيدعم LSP.

## 3. إيه علاقة LSP بالـ OCP؟

المبدأين مرتبطين ببعض:

- OCP: أقدر أضيف implementations جديدة من غير ما أعدل الكود المستقر كل مرة.
    
- LSP: الـ implementations الجديدة تقدر تحل محل النوع الأساسي من غير ما تكسر الـ behavior المتوقع.
    

يعني مش كفاية تعمل `interface` وتضيف classes جديدة؛ لازم كل implementation تلتزم بالـ contract بتاعها.

## 4. مثال مهم في الـ Interview: Rectangle وSquare

عندنا `Rectangle` فيها `setWidth()` و`setHeight()`، وعملنا `Square extends Rectangle`.

لو الـ `Square` بتفرض إن العرض والارتفاع يفضلوا متساويين، فاستدعاء `setWidth()` ممكن يغيّر الارتفاع كمان، وبالتالي يكسر توقعات الكود اللي بيتعامل مع `Rectangle`.

دي من أشهر أمثلة انتهاك LSP: الوراثة صحيحة من ناحية الشكل، لكن مش بالضرورة صحيحة من ناحية السلوك.
