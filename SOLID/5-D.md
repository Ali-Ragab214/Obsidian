# Dependency Inversion Principle (DIP)

> ملحوظة صغيرة: الاسم **Principle** مش Protocol.

## الفكرة في جملتين

1. الـ **high-level module** مايعتمدش على الـ **low-level module**. الاتنين يعتمدوا على **abstraction**.
2. الـ abstraction مايعتمدش على التفاصيل، التفاصيل هي اللي تعتمد على الـ abstraction.

## يعني إيه High-level و Low-level؟

|النوع|بيعمل إيه|أمثلة|
|---|---|---|
|**High-level**|الـ business logic: **"إيه اللي المفروض يحصل"**|`OrderService`, `NotificationService`|
|**Low-level**|التفاصيل التقنية: **"إزاي يتنفذ"**|`EmailSender`, `SmsSender`, `MySqlRepo`, `StripePayment`|

الـ high-level هو قلب التطبيق، والـ low-level أدوات بيستخدمها.

---

## الكود بدون DIP ❌

```java
// Low-level
class EmailSender {
    void send(String msg) {
        System.out.println("Email: " + msg);
    }
}

// High-level
class NotificationService {
    private EmailSender sender = new EmailSender(); // ❌ مربوط بـ Email

    void notifyUser(String msg) {
        sender.send(msg);
    }
}
```

**المشاكل:**

- `NotificationService` (high) معتمد مباشرة على `EmailSender` (low).
- عايز SMS؟ لازم **تعدل** `NotificationService`.
- مش هتقدر تعمل unit test بـ mock بسهولة.

---

## الكود مع DIP ✅

### 1) الـ Abstraction

```java
interface MessageSender {
    void send(String msg);
}
```

### 2) الـ Low-level modules (بتعتمد على الـ abstraction)

```java
class EmailSender implements MessageSender {
    @Override
    public void send(String msg) {
        System.out.println("Email: " + msg);
    }
}

class SmsSender implements MessageSender {
    @Override
    public void send(String msg) {
        System.out.println("SMS: " + msg);
    }
}
```

### 3) الـ High-level module (بيعتمد على الـ abstraction)

```java
class NotificationService {
    private final MessageSender sender; // ✅ interface مش كلاس

    NotificationService(MessageSender sender) { // Constructor Injection
        this.sender = sender;
    }

    void notifyUser(String msg) {
        sender.send(msg);
    }
}
```

### 4) التشغيل

```java
public class Main {
    public static void main(String[] args) {
        NotificationService emailNotif = new NotificationService(new EmailSender());
        emailNotif.notifyUser("Hello");   // Email: Hello

        NotificationService smsNotif = new NotificationService(new SmsSender());
        smsNotif.notifyUser("Hello");     // SMS: Hello
    }
}
```

---

## ازاي الكود بيثبت إنهم بيعتمدوا على الـ abstraction؟

شوف الـ **imports/الأنواع** اللي كل كلاس بيذكرها:

|الكلاس|بيذكر إيه جواه؟|يعتمد على|
|---|---|---|
|`NotificationService` (high)|`MessageSender` بس|✅ الـ abstraction|
|`EmailSender` (low)|`implements MessageSender`|✅ الـ abstraction|
|`SmsSender` (low)|`implements MessageSender`|✅ الـ abstraction|

**لاحظ:** كلمة `EmailSender` أو `SmsSender` **مش موجودة خالص** جوه `NotificationService`. ده الدليل إنه مش معتمد عليهم.

## الرسمة

```
❌ قبل:
NotificationService ───────► EmailSender
      (high)                   (low)

✅ بعد:
NotificationService ──► «MessageSender» ◄── EmailSender
      (high)              (abstraction)  ◄── SmsSender
                                              (low)
```

السهم اللي كان رايح من high لـ low **اتقلب**: دلوقتي الـ low هو اللي بيشاور على الـ abstraction. ده معنى **Inversion**.

## مع Spring Boot (شغلك الحقيقي)

```java
public interface MessageSender {
    void send(String msg);
}

@Component
public class EmailSender implements MessageSender {
    public void send(String msg) { /* ... */ }
}

@Service
public class NotificationService {
    private final MessageSender sender;

    public NotificationService(MessageSender sender) {
        this.sender = sender;
    }
}
```

لو عندك أكتر من implementation، حدد واحدة بـ `@Primary` أو `@Qualifier("emailSender")`.

---

## الخلاصة

- **High-level** = business logic، **Low-level** = تفاصيل التنفيذ.
- الاتنين بيتكلموا عن طريق **interface**.
- **DIP** = المبدأ، **DI/Spring** = الأداة اللي بتحقن الـ implementation.
- الفايدة: تضيف `PushSender` بكرة من غير ما تلمس `NotificationService`.
