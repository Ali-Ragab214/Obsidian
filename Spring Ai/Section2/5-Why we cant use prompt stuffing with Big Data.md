

## 1. حدود الـ Context Window (اللي هي حد الموديل نفسه)

كل LLM model عنده **حد أقصى** من الـ tokens اللي يقدر يستقبلها كـ input، وكمان حد أقصى للـ response اللي بيطلعه.  مثال بموديل GPT-4.1 اللي عنده context window حوالي مليون token للـ input، وأقصى حاجة يقدر يطلعها كـ output حوالي 32,768 token.

يعني لو عندك ملايين الصفحات أو آلاف المستندات، ومحاولتش تحطها كلها في prompt واحد، الموديل هيرفض ويديك error إنه مش قادر يستقبل الكمية دي.

## 2. التكلفة (Billing)

النقطة دي أهم من الأولى في الواقع العملي. كل request بتبعته للـ LLM بيتحول لـ **tokens**، وأي provider زي OpenAI أو Gemini أو Azure بيحاسبك على أساس عدد الـ tokens دي (input + output).

يعني لو عندك سياسة شركة أو دوكيومنت كبير (100 صفحة مثلاً)، وعملت prompt stuffing، **كل مرة** حد يسأل سؤال، انت هتبعت الـ 100 صفحة دي كاملة تاني كـ context، وتتحاسب عليها من الأول. لو الناس بتسأل كتير، الفاتورة هتبقى ضخمة جدًا وغير منطقية اقتصاديًا.

---

## يعني ببساطة

**Prompt Stuffing** كويس بس مع **البيانات الصغيرة** (ملف أو اتنين، صفحة أو اتنين) اللي بتتقال في المستند إنها "simple scenarios".

لكن لو عندك **بيانات كبيرة** (زي مكتبة documents، أو تاريخ كامل من الـ transactions)، هنا لازم تستخدم حاجة زي **RAG**، لأن الفكرة فيه إنك بتجيب بس **الجزء اللي محتاجه فعلاً** من الداتا (مش كل حاجة)، فبتوفر في التوكنز وبتتفادى مشكلة الحد الأقصى للموديل.
