بص، هو هنا **بيطبق فكرة الـ Custom Advisor عمليًا**، والهدف الأساسي مش إنك تحفظ الكود، لكن تفهم **ليه عمل Advisor أصلًا وإزاي الـ Advisor يقدر يمسك الـ Request والـ Response ويعمل Logic بينهم**.

خلينا نلحم الكلام كله ببعضه.

```java 
package com.example.openai.advisors;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.ai.chat.client.ChatClientRequest;
import org.springframework.ai.chat.client.ChatClientResponse;
import org.springframework.ai.chat.client.advisor.api.CallAdvisor;
import org.springframework.ai.chat.client.advisor.api.CallAdvisorChain;
import org.springframework.ai.chat.metadata.Usage;
import org.springframework.ai.chat.model.ChatResponse;


public class TokenUsageAuditAdvisor  implements CallAdvisor {
private static final Logger logger = LoggerFactory.getLogger(TokenUsageAuditAdvisor.class);
    @Override
    public ChatClientResponse adviseCall(ChatClientRequest chatClientRequest, CallAdvisorChain callAdvisorChain) {
        ChatClientResponse response = callAdvisorChain.nextCall(chatClientRequest);
        ChatResponse chatResponse = response.chatResponse();
        if(chatResponse != null && chatResponse.getMetadata() != null)
        {
            Usage usage = chatResponse.getMetadata().getUsage();
            if(usage != null)
            {
                logger.info("Token Usage: " + usage);
            }
        }
        return response;
    }

    @Override
    public String getName() {
        return "CallAdvisor";
    }

    @Override
    public int getOrder() {
        return 1;
    }
}

```

```text
   ↓

   ↓
```
```text
[Custom Advisor]
   ↓
```

# 6. أهم واحدة: `adviceCall()`

دي قلب الـ Advisor.

هي اللي بتسمحلك تتحكم في الـ flow.

الفكرة تقريبًا:

```java
public ChatClientResponse adviseCall(
        ChatClientRequest request,
        CallAdvisorChain chain) {

    ChatClientResponse response = chain.nextCall(request);

    // custom logic

    return response;
}
```

ركز هنا جدًا:

```java
chain.nextCall(request)
```

دي معناها:

> كمل الـ chain وروح نفذ اللي بعدي، وفي الآخر هاتلي الـ response.

يعني:

```text
Advisor
   ↓
chain.nextCall()
   ↓
LLM
   ↓
Response
   ↓
Advisor
```

وبالتالي الـ Advisor قدر يمسك الـ Response **بعد ما الـ LLM رجعه**.

وده السبب إنه يقدر يعرف الـ tokens.

# 9. يعني إيه Prompt / Completion / Total؟

دي نقطة لازم تكون فاهمها جدًا.

### Prompt Tokens

الـ input اللي أنت بعته للـ LLM.

مثلاً:

```text
"Explain Java records"
```

ده بيتحول إلى Tokens.

---

### Completion Tokens

الـ output اللي الـ LLM رجعه.

مثلاً:

```text
"A record is a special kind of class..."
```

وده بيتحول برضه لـ Tokens.

---

### Total Tokens

غالبًا:

```text
Total Tokens
=
Prompt Tokens
+
Completion Tokens
```

مثلاً:

```text
Prompt       = 90
Completion   = 82

Total        = 172
```

# 10. ليه الـ Prompt Stuffing غالي؟

دي من أهم الحاجات اللي كان عايز يوضحها.

لو أنت بتبعت للـ LLM كمية Data ضخمة:

```text
Prompt
+ User Question
+ Huge Context
+ Documents
+ Previous Messages
```

الـ input tokens هتزيد جدًا.

مثلاً:

```text
Normal request:

Input  = 100 tokens
Output = 50 tokens
Total  = 150
```

لكن:

```text
Prompt Stuffing:

Input  = 10,000 tokens
Output = 500 tokens
Total  = 10,500
```

فحتى لو الـ output صغير، أنت دفعت على كمية الـ input الكبيرة.

وده أحد الأسباب المهمة اللي بتخلي تقنيات زي **RAG** مفيدة: بدل ما تبعت كل الـ data للـ LLM، تجيب فقط الـ relevant context.

# 11. إيه قصة `getOrder()`؟

الـ Advisor ممكن يكون عندك منه أكتر من واحد.

مثلاً:

```text

TokenUsageAuditAdvisor
SecurityAdvisor
RAGAdvisor
```

فلازم تحدد مين يشتغل الأول.

مثلاً:

```java
getOrder() {
    return 1;
}
```

و:

```text
SimpleLoggerAdvisor = 0
TokenUsageAuditAdvisor = 1
```

فالترتيب بيكون حسب الـ order.

الفكرة المهمة:

> **كل ما الـ order value تكون أعلى/أقل حسب ترتيب Spring AI المستخدم، المهم إن الـ advisors بتتطبق وفق ترتيبها المحدد.**

وفي المثال بتاع المحاضر، هو اعتبر `TokenUsageAuditAdvisor` له أولوية أعلى من الـ logger بسبب ترتيب الـ advisors اللي ضبطه.

# 16. نقطة مهمة جدًا: الـ Advisor مش هو اللي بيحسب الـ Tokens

دي نقطة لازم تفرق بينها.

الـ Advisor **لا يقوم بتقسيم الـ prompt وحساب tokens بنفسه**.

هو فقط:

```text
LLM
 ↓
returns token usage metadata
 ↓
Advisor reads it
 ↓
logs/saves it
```

يعني الـ LLM provider هو اللي بيحسب الاستخدام، والـ Advisor بيقرأ النتيجة.

# 17. طب ليه قال إن الكود Specific لـ OpenAI؟

لأن كل provider ممكن يرجع الـ metadata بطريقة مختلفة.

مثلاً:

```text

    ↓
usage
    ├── promptTokens
    ├── completionTokens
    └── totalTokens
```

Provider تاني ممكن يسميهم بشكل مختلف أو يحطهم في مكان مختلف.

فلو عملت:

```java
metadata.getUsage()
```

بالطريقة دي، لازم تكون فاهم **إزاي الـ provider اللي أنت بتستخدمه بيرجع usage information**.

# 20. وده شكل الـ flow اللي لازم تحفظه

```text
User
 │
 ▼
Controller
 │
 ▼
ChatClient
 │
 ▼
Advisor Chain
 │
 ├── SimpleLoggerAdvisor
 │
 └── TokenUsageAuditAdvisor
 │
 ▼
LLM Provider
 │
 ▼
ChatResponse
 │
 └── Metadata
       │
       └── Usage
            ├── Prompt Tokens
            ├── Completion Tokens
            └── Total Tokens
 │
 ▼
TokenUsageAuditAdvisor
 │
 ├── Log
 ├── Calculate Cost
 └── Save to DB
```

**فأهم 4 حاجات من الفيديو:**

1. **Advisor = interceptor/middleware حوالين LLM call.**
    
2. **Custom Advisor تقدر تعمل فيه أي logic أنت محتاجه.**
    
3. **Token usage موجود في الـ response metadata بعد ما الـ LLM يرد.**
    
4. **لو الـ Advisor مش خاص بـ endpoint واحد، حطه كـ default advisor في `ChatClient` بدل ما تكرره في كل Controller.**
    

وده أساس مهم جدًا لأن بعد كده لما تدخل **RAG / Memory / Security / Observability / Logging** هتلاقي الـ Advisors داخلة في حاجات كتير.
