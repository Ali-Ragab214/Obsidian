# 📦 Database Migrations in Spring Boot (Flyway Explained)

---

# 1) 🧠 المشكلة الأساسية بدون Migration Tools

في أي مشروع Spring Boot، أثناء التطوير ممكن تستخدم:

- إنشاء جداول تلقائيًا
    
- تعديل schema
    
- حذف columns
    
- إضافة relations
    

لو اعتمدت على التطبيق نفسه في إدارة الداتابيز، زي:

```properties
spring.jpa.hibernate.ddl-auto=update
```

أو:

```properties
create / create-drop / update / validate
```

👉 المشكلة هنا:  
التطبيق أصبح مسؤول عن الداتابيز (وهذا خطر جدًا في production)

---

# 2) ⚙️ معنى ddl-auto options في Hibernate

## 1. create

- بيحذف كل الجداول ويعيد إنشائها كل مرة
    
- مناسب للتجارب فقط
    

---

## 2. create-drop

- ينشئ الجداول عند التشغيل
    
- ويحذفها عند إيقاف التطبيق
    

---

## 3. update

- يحاول يعدل schema تلقائيًا
    
- ممكن:
    
    - يضيف columns
        
    - لكنه لا يضمن consistency  
        ❌ خطر جدًا في production
        

---

## 4. validate ⭐

- لا يعدل أي شيء
    
- فقط يتأكد أن الـ schema مطابق للـ entities
    
- لو في اختلاف → يطلع error
    

👉 ده الأكثر أمانًا مع Hibernate لكنه لا يحل مشكلة versioning

---

## 🚨 ليه ddl-auto غير مناسب في Production؟

لأن:

- التغييرات غير tracked
    
- مفيش history للتعديلات
    
- ممكن data corruption
    
- behavior غير متوقع بين environments
    
- كل deploy ممكن يغير DB بطريقة مختلفة

# 4) 🪶 فكرة Flyway ببساطة

Flyway يعمل كالتالي:

> “أنا عندي سجل بكل التغييرات (versions) على قاعدة البيانات، وكل مرة أشغّل التطبيق أطبق الجديد فقط”

---

# 5) 🧭 كيف Flyway يعمل (Behind the scenes)

## عند تشغيل التطبيق:

```text
Spring Boot starts
        ↓
Flyway starts automatically
        ↓
Flyway يبحث عن migration scripts
        ↓
يقارنها بجدول اسمه:
    flyway_schema_history
        ↓
ينفذ الملفات الجديدة فقط
        ↓
يسجل كل migration تم تنفيذه
```

---

# 6) 🗂️ مكان ملفات Flyway

افتراضيًا:

```
src/main/resources/db/migration/
```

---

# 7) 📄 Naming Convention (المهم جدًا)

الشكل الصحيح:

```text
V1__init_database.sql
V2__add_users_table.sql
V3__alter_orders_add_column.sql
```

---

## 📌 Pattern breakdown:

```text
V<version>__<description>.sql
```

### مثال:

```text
V1__init_database.sql
```

|جزء|معنى|
|---|---|
|V1|رقم النسخة|
|__|separator (double underscore)|
|init_database|وصف التغيير|
|.sql|SQL script|

---

# 8) 🧾 مثال Migration File

## V1__init_database.sql

```sql
CREATE TABLE users (
    id BIGSERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(150) UNIQUE NOT NULL
);
```

---

## V2__add_phone_column.sql

```sql
ALTER TABLE users
ADD COLUMN phone VARCHAR(20);
```

---

# 9) ⚙️ Dependency في Spring Boot

## Flyway core:

```xml
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-core</artifactId>
</dependency>
```

## PostgreSQL support (اختياري في بعض الإصدارات):

```xml
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-database-postgresql</artifactId>
</dependency>
```

# 10) ⚙️ Application Properties

```properties
spring.flyway.locations=classpath:db/migration
spring.flyway.baseline-on-migrate=true
```

# 11) 🧠 Flyway Schema History Table

Flyway بيعمل table تلقائي:

```text
flyway_schema_history
```

## فيها:

|column|meaning|
|---|---|
|version|رقم migration|
|description|الوصف|
|type|SQL|
|checksum|للتحقق من التعديل|
|success|هل نجح التنفيذ|

# 13) 🚀 Flyway vs Hibernate ddl-auto

|Feature|Hibernate ddl-auto|Flyway|
|---|---|---|
|Schema control|Automatic|Manual scripts|
|Versioning|❌ No|✅ Yes|
|Production safe|❌ No|✅ Yes|
|Rollback support|❌ Weak|⚠️ manual strategy|
|Team collaboration|❌ risky|✅ safe|
|History tracking|❌ None|✅ full history|

# 15) 🧩 Best Practices

- كل تغيير = ملف جديد (never edit old migration)
    
- naming consistent
    
- test migrations locally before prod
    
- keep migrations small
    
- avoid logic inside SQL beyond schema changes
