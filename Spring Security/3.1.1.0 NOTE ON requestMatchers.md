❌ الإجابة دي مش صحيحة، وده بالضبط السؤال اللي بيكشف فهم ترتيب الـ `requestMatchers`.

الكود:

```java
http.authorizeHttpRequests(auth -> auth
    .requestMatchers("/api/**").permitAll()
    .requestMatchers("/api/admin/**").hasRole("ADMIN")
    .anyRequest().authenticated()
);
```

والـ Request:

```http
GET /api/admin/users
```

---

### إيه اللي بيحصل؟

Spring Security بيقرأ الـ Matchers **بالترتيب**.

أول Matcher:

```java
.requestMatchers("/api/**").permitAll()
```

هل:

```text
/api/admin/users
```

يطابقه؟

✅ نعم.

إذن Spring Security يتوقف هنا ويقول:

> Permit All

ولا يروح أصلًا للسطر ده:

```java
.requestMatchers("/api/admin/**").hasRole("ADMIN")
```

---

### النتيجة

✅ **B = 200 OK**

حتى لو المستخدم:

- USER
    
- ADMIN
    
- أو مش عامل Login أصلًا
    

لأن أول Rule سمحت له.

---

# القاعدة الذهبية

ضع الـ Rules الأكثر تحديدًا أولًا:

✅ صح:

```java
http.authorizeHttpRequests(auth -> auth
    .requestMatchers("/api/admin/**").hasRole("ADMIN")
    .requestMatchers("/api/**").permitAll()
    .anyRequest().authenticated()
);
```

❌ خطأ:

```java
.requestMatchers("/api/**").permitAll()
.requestMatchers("/api/admin/**").hasRole("ADMIN")
```

لأن الثانية لن تُنفذ أبدًا.

# سؤال 5 (HTTP Methods)

عندك:

```java
http.authorizeHttpRequests(auth -> auth
    .requestMatchers(HttpMethod.GET, "/api/products/**").permitAll()
    .requestMatchers(HttpMethod.POST, "/api/products/**").hasRole("ADMIN")
    .anyRequest().authenticated()
);
```

ما النتيجة؟

### A

```http
GET /api/products
```

### B

```http
POST /api/products
```

بمستخدم:

```text
ROLE_USER
```

### C

```http
POST /api/products
```

بمستخدم:

```text
ROLE_ADMIN
```

اكتب:

```text
A =
B =
C =
```

وده من أكتر الاستخدامات المنتشرة في REST APIs. 😎
