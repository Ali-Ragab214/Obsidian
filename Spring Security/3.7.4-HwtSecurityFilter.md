# الفكرة العامة للفيلتر

الفيلتر ده بيشتغل مع **كل request** وبيسأل سؤال واحد:

> هل الـ request ده جايب JWT صحيح؟  
> لو آه → نعتبر المستخدم logged in  
> لو لأ → نسيبه يكمل بدون login

---

# 1️⃣ قراءة Authorization Header

final String authHeader = request.getHeader("Authorization");

أي request فيه JWT لازم يكون فيه header بالشكل ده:

Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...

لو مفيش header أصلاً → يبقى user مش عامل login.

---

# 2️⃣ التأكد إن التوكن من نوع Bearer

if(authHeader == null || !authHeader.startsWith("Bearer "))  
{  
    filterChain.doFilter(request,response);  
    return;  
}

ليه الشرط ده مهم؟

لأن مش كل endpoints محتاجة login:

- register
- login
- public APIs

فلو مفيش توكن:  
👉 سيب الطلب يكمل عادي بدون authentication.

دي نقطة مهمة جداً.

---

# 3️⃣ استخراج التوكن من الهيدر

jwt = authHeader.substring(7);

ليه 7 ؟ 🤔

كلمة:

Bearer␣

= 7 حروف.

إحنا بنشيلها ونسيب التوكن بس.

---

# 4️⃣ استخراج اليوزر من التوكن

userEmail = jwtService.extractUsername(jwt);

دلوقتي:

- فكينا التوكن
- طلعنا الـ username (أو email)

بس كده مش كفاية نثق فيه ❌

ليه؟  
لأن التوكن ممكن يكون:

- متزوّر
- منتهي
- معمول ليوزر تاني

فلازم نتحقق.

---

# 5️⃣ نتأكد إن مفيش Authentication موجود

SecurityContextHolder.getContext().getAuthentication() == null

ليه الشرط ده مهم جداً؟ 🔥

ممكن يكون فيه Filter قبلك عمل authentication.  
فما ينفعش نعمله مرتين.

لو فيه Authentication بالفعل → خلاص سيب الطلب يكمل.

---

# 6️⃣ تحميل المستخدم من الداتابيز

UserDetails userDetails = userDetailsService.loadUserByUsername(userEmail);

دلوقتي بقينا نملك مصدرين للمعلومات:

|المصدر|البيانات|
|---|---|
|JWT|username|
|Database|userDetails الحقيقي|

دلوقتي نبدأ نتحقق.

---

# 7️⃣ التحقق من التوكن

if(jwtService.isTokenValid(jwt,userDetails))

الميثود دي بتتأكد من:

- التوقيع صحيح 🔐
- التوكن مش منتهي ⏰
- التوكن معمول لنفس المستخدم 👤

لو أي حاجة غلط → authentication مش هيتعمل.

---

# 8️⃣ إنشاء Authentication Object ⭐ أهم خطوة

UsernamePasswordAuthenticationToken authToken =  
        new UsernamePasswordAuthenticationToken(  
                userDetails,  
                null,  
                userDetails.getAuthorities()  
        );

هنا بنقول لـ Spring Security:

> المستخدم ده خلاص authenticated ✅

وبندي له:

- بيانات المستخدم
- الصلاحيات (roles)

---

# 9️⃣ إضافة تفاصيل الـ request

authToken.setDetails(  
    new WebAuthenticationDetailsSource().buildDetails(request)  
);

ده بيضيف معلومات زي:

- IP
- session id

مش أساسي لكن Best Practice.

---

# 🔟 تخزين المستخدم في Security Context

SecurityContextHolder.getContext().setAuthentication(authToken);

ده أهم سطر في الفيلتر كله 🔥

من اللحظة دي:  
Spring بقى شايف إن المستخدم Logged in.

أي Controller يقدر يجيب المستخدم الحالي بسهولة.

---

# آخر خطوة: السماح للطلب يكمل

filterChain.doFilter(request,response);

دي معناها:

> خلّي الطلب يكمل لباقي الفلاتر وبعدين الـ Controllers.

لو نسيت السطر ده → كل API هيتقفل 💀

---

# هل الكود ده ثابت في كل مشاريع JWT؟

الـ FLOW ثابت جداً:

1️⃣ قراءة header  
2️⃣ استخراج التوكن  
3️⃣ استخراج username  
4️⃣ تحميل user من DB  
5️⃣ التحقق من التوكن  
6️⃣ إنشاء Authentication  
7️⃣ وضعه في SecurityContext  
8️⃣ السماح للطلب يكمل

أي مشروع Spring + JWT هتلاقي نفس الخطوات تقريباً.

---

# ملحوظة صغيرة احترافية 👌

المفروض تضيف try/catch حول استخراج التوكن عشان لو التوكن بايظ ما يكسّرش الـ request.

بس غير كده الكود ممتاز 👍

---

لو حابب نشرح بعد كده إزاي نضيف الفيلتر في SecurityConfig عشان يشتغل فعلاً في الـ filter chain، دي آخر قطعة في البازل 😎
