سؤال ممتاز، ودي أكتر نقطة الناس بتتلخبط فيها في الـ Idempotency.

الإجابة المختصرة:

> **الـ UUID مش بيتولد لكل ضغطة زر.**
> 
> **الـ UUID بيتولد لكل "عملية دفع" (Payment Attempt)، ولو حصل Retry لازم يتبعت نفس الـ UUID.**

وده الفرق المهم جدًا.

```

```

وبعت

```

- حفظ الـ UUID ✅
    

---

بعد ساعة

اليوزر قرر يشتري نفس المنتج تاني.

ضغط

Pay
```

الـ Frontend هيعمل UUID جديد

```
xyz-999
```

وده طبيعي جدًا.

ليه؟

لأن دي **عملية دفع جديدة**.

إذن لازم تتنفذ.

# يبقى السؤال المهم

## إمتى الـ UUID بيتغير؟

كل **عملية Business جديدة**.

مثلاً

```
شراء كتاب
```

↓

UUID

```
111
```

---

بعد أسبوع

```
شراء موبايل
```

↓

UUID

```
222
```

---

لكن

```
Retry لنفس شراء الكتاب
```

↓

لازم

```
111
```

مش

```
333
```

# مين اللي بيولد الـ UUID؟

غالبًا

**الـ Frontend**

يعني React أو Flutter أو Android أو iOS.

مثلاً في React:

```javascript
const key = crypto.randomUUID();
```

ويفضل محتفظ بيه في الـ State أو Local Storage لحد ما العملية تنجح أو تفشل نهائيًا.

---

# ليه منخليش الـ Backend يولده؟

لو الـ Backend هو اللي ولد الـ UUID،

إزاي الـ Client هيعرفه لو الـ Response ضاع؟

مثلاً:

```
Client -----> Server
```

السيرفر ولد UUID.

خصم الفلوس.

لكن الـ Response وقع.

الـ Client معندوش أي فكرة عن الـ UUID.

هيبعت Request جديد.

فالسيرفر هيعتبرها عملية جديدة.

إذن الحل ده مش هينفع.

---

# تخيلها كأنها إيصال

كل محاولة شراء لها "رقم إيصال".

لو الإيصال ضاع في الطريق،

أنت بتقول للكاشير:

> "أنا بدفع بنفس الإيصال رقم 123."

مش بتقول:

> "اعمللي إيصال جديد."

---

### قاعدة احفظها للإنترفيو

> **Idempotency Key identifies the operation, not the request.**

يعني الـ **Idempotency Key بيمثل العملية نفسها (عملية الدفع)**، وليس كل HTTP Request.

فأي **Retry لنفس العملية** يستخدم **نفس المفتاح**، أما **عملية دفع جديدة** فتستخدم **Idempotency Key جديد**. دي الفكرة الأساسية اللي بتبني عليها كل أنظمة الدفع الاحترافية.
