أيوه، هنا **الـ architecture اللي أنت كاتبه بتغيّر طريقة التفكير شوية** عن `CourseService + CourseServiceImpl`.

والإجابة المختصرة جدًا:

> **لا، مش هتحقن كل الـ Handlers في الـ Controller.**  
> غالبًا هتستخدم **Mediator**، أو تعمل Facade/Application Service لو مش عايز Mediator.

خليني أوضح الفلو الصح عندك.

---

## 1. في الـ Architecture دي مفيش `CourseServiceImpl`

أنت عندك:

```text
Command
   ↓
Handler
   ↓
Domain
   ↓
Repository
```

مثلاً:

```text
CreateCourseCommand
        ↓
CreateCourseHandler
        ↓
Course
        ↓
CourseRepository
```

و:

```text
UpdateCourseCommand
        ↓
UpdateCourseHandler
        ↓
Course
        ↓
CourseRepository
```

كل **Use Case** له Handler خاص بيه.

وده أصلًا من أفكار **CQRS**.

# 3. الحل: Mediator

بتخلي الـ Controller يتعامل مع **Mediator واحد فقط**.

مثلاً:

```java
private final CourseMediator mediator;
```

وبعدين:

```java
@PostMapping
public CourseResponse create(
        @RequestBody CreateCourseRequest request) {

    return mediator.send(
        new CreateCourseCommand(request)
    );
}
```

والـ Mediator يقول:

```text
CreateCourseCommand
        ↓
"مين الـ Handler بتاعي؟"
        ↓
CreateCourseHandler
```

ولو:

```java
mediator.send(new UpdateCourseCommand(...))
```

يروح:

```text
UpdateCourseCommand
        ↓
UpdateCourseHandler
```

وهكذا.

# 4. الصورة كاملة

الـ Controller عندك يبقى بسيط جدًا:

```text
                CourseController
                       │
                       │
                 CourseMediator
                       │
          ┌────────────┼─────────────┐
          ↓            ↓             ↓
      Command        Command        Query
          │            │             │
          ↓            ↓             ↓
      Create         Update         Get
      Handler        Handler        Handler
```

فبدل:

```text
Controller
   ↓
7 Handlers
```

عندك:

```text
Controller
   ↓
1 Mediator
   ↓
Correct Handler
```

# 5. وده شبه MediatR في .NET

بما إنك اشتغلت قبل كده بـ **MediatR** في .NET، فالفكرة دي هتكون مألوفة جدًا ليك.

في .NET:

```csharp
await _mediator.Send(new CreateCourseCommand(...));
```

وفي Spring تقدر تعمل نفس الـ concept باستخدام:

- **Spring Modulith Application Events** في سيناريوهات معينة
    
- أو **Axon Framework** لو داخل CQRS/Event Sourcing
    
- أو تعمل **Mediator بسيط بنفسك**
    
- أو تستخدم library مناسبة
    

لكن **مش لازم تستخدم Framework مخصوص عشان تطبق CQRS**.

# 6. طيب الـ Handler نفسه؟

مثلاً:

```java
@Component
public class CreateCourseHandler {

    private final CourseRepository courseRepository;

    public CourseResponse handle(CreateCourseCommand command) {

        // business/application logic

        Course course = new Course(...);

        courseRepository.save(course);

        return ...;
    }
}
```

الـ Handler هو المسؤول عن **Use Case واحد**.

يعني:

```text
CreateCourseHandler
        ↓
Create Course

UpdateCourseHandler
        ↓
Update Course

PublishCourseHandler
        ↓
Publish Course

ArchiveCourseHandler
        ↓
Archive Course
```

وده عكس الـ `CourseServiceImpl` القديم اللي كان ممكن يبقى:

```text
CourseServiceImpl
 ├── create()
 ├── update()
 ├── publish()
 ├── archive()
 ├── get()
 ├── search()
 └── ...
```

وده بيخلي كل class صغير ومركز.

# 8. طب هل لازم Mediator؟

**لا.**

ممكن تعمل مثلاً:

```java
@RestController
public class CourseController {

    private final CreateCourseHandler createHandler;
    private final UpdateCourseHandler updateHandler;
}
```

وده **مش غلط تقنيًا**.

لكن لو عندك 10 أو 15 Handler، الـ Controller هيبدأ يبقى مليان Dependencies.

عشان كده **Mediator pattern** بيحل المشكلة دي بشكل أنضف.

---

# 9. والأهم: الـ Repository عندك

عندك:

```text
domain/
   repository/
      CourseRepository.java
```

ده Interface:

```java
public interface CourseRepository {

    Optional<Course> findById(Long id);

    Course save(Course course);
}
```

وبعدين Infrastructure:

```java
public interface CourseJpaRepository
        extends JpaRepository<CourseEntity, Long> {
}
```

والـ Adapter:

```java
@Component
public class CourseRepositoryImpl
        implements CourseRepository {

    private final CourseJpaRepository jpaRepository;

    // ...
}
```

فالـ Handler يعمل:

```java
private final CourseRepository repository;
```

مش:

```java
CourseJpaRepository
```

وده يحقق Dependency Inversion بشكل ممتاز:

```text
Application
     ↓
Domain abstraction
     ↑
Infrastructure implementation
```

# الخلاصة المهمة جدًا

الـ architecture بتاعتك ماشية كده:

```text
HTTP
 │
 ▼
CourseController
 │
 ▼
Mediator
 │
 ├──── CreateCourseCommand
 │            ↓
 │      CreateCourseHandler
 │
 ├──── UpdateCourseCommand
 │            ↓
 │      UpdateCourseHandler
 │
 ├──── PublishCourseCommand
 │            ↓
 │      PublishCourseHandler
 │
 └──── GetCourseQuery
              ↓
        GetCourseHandler
              │
              ▼
       Domain / Entity
              │
              ▼
      CourseRepository
              ▲
              │
      CourseRepositoryImpl
              │
              ▼
        JPA Repository
              │
              ▼
          PostgreSQL
```

**فأنت مش بتستبدل `CourseService` بـ 10 dependencies في الـ Controller.**

أنت بتستبدل:

```text
Controller → CourseService
```

بـ:

```text
Controller → Mediator → Specific Handler
```

وده واحد من الأسباب اللي بتخلي **CQRS + Vertical/Feature-based Architecture** مناسبين جدًا لما عدد الـ use cases يكبر.
