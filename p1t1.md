### 1. تعديلات جدول `stock_mvts` (الموجود من V1)

**Columns جديدة:**

**Indexes:**

|   |   |   |
|---|---|---|
|Index|على|الفايدة|

|`idx_stock_mvts_product_date`|`(product_id, date_mvt)`|استعلامات التقارير اليومية|
|`idx_stock_mvts_reason_occurred`|`(reason, occurred_at)`|تسريع الفلترة بالسبب والوقت|

### 2. جدول `stock_balances` (جديد)

- `product_id` من نوع `VARCHAR(255) NOT NULL PRIMARY KEY`، مع Foreign Key اسمه `fk_stock_balances_product` على `products(id)`.
- `on_hand INTEGER NOT NULL DEFAULT 0` و `reserved INTEGER NOT NULL DEFAULT 0`.
- `version BIGINT NOT NULL DEFAULT 0` لدعم الـ Optimistic Locking (`@Version`).
- `updated_at TIMESTAMP(6) NOT NULL DEFAULT now()`.
- `CONSTRAINT chk_on_hand_non_negative CHECK (on_hand >= 0)` بيمنع الرصيد السالب على مستوى الـ DB نفسها.

### 3. جدول `stock_counts` (جديد)

- أعمدة الـ audit القياسية: `id`, `created_at`, `created_by`, `deleted`, `updated_at`, `updated_by`.
- `product_id VARCHAR(255) NOT NULL` مع FK اسمه `fk_stock_counts_product`.
- `counted_qty INTEGER NOT NULL` (الجرد الفعلي).
- `system_qty INTEGER NOT NULL` (رصيد النظام لحظة الجرد).
- `variance INTEGER NOT NULL` (الفرق = `counted_qty - system_qty`).
- `note TEXT` و `counted_by VARCHAR(255) NOT NULL` و `counted_at TIMESTAMPTZ NOT NULL DEFAULT now()`.
- `adjustment_movement_id VARCHAR(255)` مع FK اسمه `fk_stock_counts_adjustment` على `stock_mvts(id)`، وهو nullable لأن لو `variance == 0` مفيش حركة تسوية بتتعمل.
- Index: `idx_stock_counts_product_counted` على `(product_id, counted_at DESC)`.

> **ملاحظة:** الـ PostgreSQL immutability trigger الاختياري (`BEFORE UPDATE OR DELETE ON stock_mvts`) **لم يُضف** في V3. حماية الـ append-only بتتم على مستوى الـ Service والـ Repository والـ Controller والـ Security.

## Phase 3 — Repositories

**المسار:** `repositories/`

### `StockMvtRepository`

- يرث `JpaRepository<StockMvt, String>` و `JpaSpecificationExecutor<StockMvt>` (لتشغيل استعلامات التاريخ بالفلترة الديناميكية من غير مشاكل PostgreSQL مع `:param IS NULL`).
- `sumInQuantityByProductId(productId)` و `sumOutQuantityByProductId(productId)`: حساب مجموع حركات IN و OUT (مع `deleted = false`) لإعادة حساب الرصيد.
- `findAllByProductIdOrderByOccurredAtAsc(productId)`: استرجاع الحركات مرتبة زمنياً لتحديث `balanceAfter` عند الـ recompute.
- تم **إزالة** `softDeleteByProductId` نهائياً في التعديل الأخير.

### `StockBalanceRepository`

- `findByProductIdForUpdate(productId)`: عليه `@Lock(LockModeType.PESSIMISTIC_WRITE)` عشان يعمل `SELECT ... FOR UPDATE` ويقفل صف الرصيد طول مدة الـ transaction.
- `findLowStockBalances()`: استعلام JPQL بيعمل join مع `Product`، بشرط `p.deleted = false` و `sb.onHand <= p.alertThreshold`، ومرتب بـ `(p.alertThreshold - sb.onHand) DESC`.

### `StockCountRepository`

- `findByProductId(productId, pageable)`: لاستعراض عمليات الجرد لمنتج معين.

## Phase 5 — Services & Business Logic

### 1. `StockMvtService` و `StockMvtServiceImpl`

- اتفصل عن `BasicService<StockMvtRequest, StockMvtResponse>` واتشال منه `update()` و `delete()` تماماً، لضمان عدم وجود أي مسار تعديل أو حذف على الـ ledger.
- **حد معروف:** ميثود `create()` القديمة لسه موجودة على `/api/v1/stock-mvts` ومبتحدّثش `stock_balances`. الـ API الجديدة المعتمدة هي `/api/v1/stock/**`.

### 2. `StockLedgerService` و `StockLedgerServiceImpl`

**`postMovement(request)`** (`@Transactional`):

1. بيتأكد إن المنتج موجود ومش محذوف (`findByIdAndDeletedFalse`).
2. بيقفل صف الرصيد عبر `getOrCreateBalanceLocked(productId)`، اللي بينادي `findByProductIdForUpdate`. ولو مفيش صف بيعمل `StockBalance` جديد من غير ضبط `version`، عشان Spring Data JPA يعامله كـ persist مش merge.
3. لو النوع **OUT**: بيحسب `onHand - quantity`، ولو أقل من 0 والسبب مش `COUNT_ADJUSTMENT` بيرمي `InsufficientStockException` (409).
4. بيحدّث `onHand`، وبيبني `StockMvt` بـ `balanceAfter = balance.getOnHand()`، وبيحفظ الاثنين في نفس الـ transaction، وبعدها بينشر `StockMovementPostedEvent`.

**`receiveStock(request)`** (`@Transactional`):

- بيقفل صف الرصيد، يزود `onHand`، ويسجل حركة **IN** بسبب `PURCHASE_RECEIPT` مع `sourceType = "PURCHASE_ORDER"` (لو `purchaseOrderId != null`) و `unitCost`، وبعدها بينشر `StockMovementPostedEvent`.

**`getBalance(productId)`** (`readOnly = true`):

- لو المنتج ملوش صف في `stock_balances` لسه، بيرجع رصيد افتراضي `onHand = 0` و `reserved = 0`.

**`recomputeBalance(productId)`** (`@Transactional`):

- بيقفل صف الرصيد، ويحسب `sumIn - sumOut` من `StockMvtRepository`، ويحدّث `onHand`.
- بيمشي على كل الحركات بالترتيب الزمني (`occurredAt ASC`) لإعادة حساب `balanceAfter` لكل حركة.

**`getMovementHistory(...)`** (`readOnly = true`):

- بيبني `Specification<StockMvt>` ديناميكي للفلترة بـ `productId` و `deleted = false` و `type` و `from` و `to`، مع `Sort.by(DESC, "occurredAt")`، وبيرجع `PageResponse<StockMovementResponse>`.

**`getLowStockItems()`** (`readOnly = true`):

- بيجيب المنتجات اللي `on_hand <= alert_threshold` من `findLowStockBalances()`.

### 3. `StockCountService` و `StockCountServiceImpl`

**`recordCount(request)`** (`@Transactional`):

1. بيجيب المنتج النشط، ويقفل صف الرصيد (`findByProductIdForUpdate`).
2. بياخد لقطة `systemQty = balance.getOnHand()` ويحسب `variance = countedQty - systemQty`.
3. لو `variance != 0`: بيعمل حركة **IN** (لو `variance > 0`) أو **OUT** (لو `variance < 0`) بكمية `Math.abs(variance)` وبسبب `COUNT_ADJUSTMENT`، ويحدّث `balance.setOnHand(countedQty)`، وينشر `StockMovementPostedEvent`.
4. بيحفظ سجل `StockCount` بالـ actor الحالي من `AuditorAware<String>` و `adjustmentMovement` (أو `null` لو `variance == 0`).

## Phase 8 — Product Soft Delete & Append-only Fix

### المشكلة الأصلية

كان `ProductServiceImpl.delete(String id)` بينادي `stockMvtRepository.softDeleteByProductId(id)`، اللي كانت بتنفذ:

```sql
update StockMvt s set s.deleted = true where s.product.id = :productId
```

### سبب التعارض مع الـ Append-Only

1. تعديل صفوف `stock_mvts` (`UPDATE ... SET deleted = true`) بيكسر قاعدة إن الـ ledger append-only ومبيتعدلش أو يتمسح.
2. وجود `@SQLRestriction("deleted = false")` على `StockMvt` كان بيخفي تاريخ الحركات بالكامل بمجرد حذف المنتج.

### التعديل المنفّذ

- إزالة استدعاء `softDeleteByProductId(id)` وإزالة الـ dependency `StockMvtRepository` من `ProductServiceImpl`.
- إزالة `softDeleteByProductId` و `@Modifying` من `StockMvtRepository`.
- الحذف الناعم للمنتج (`this.repository.delete(product)`) بينفّذ `UPDATE products SET deleted = true WHERE id = ?` (بسبب `@SQLDelete` على `Product`). فصف المنتج بيفضل موجود في الـ DB، ومبيحصلش cascade delete على `fk_product_id`، وبتفضل صفوف `stock_mvts` سليمة تماماً (`deleted = false`).

### القيد الحالي الموثّق

لأن `getMovementHistory()` و `recomputeBalance()` بينادوا `findProductOrThrow(productId)` (اللي بيستخدم `findByIdAndDeletedFalse`)، الاتنين بيرموا `EntityNotFoundException` لو المنتج اتعمله soft delete. بينما السجلات نفسها محفوظة في `stock_mvts` ومتاحة عبر `stockMvtRepository.findAll()` واستعلامات الـ SQL المباشرة.

## Complete Runtime Flow

### 1. الموظف بيسجل حركة IN

`StockController.postMovement` ← `StockLedgerServiceImpl.postMovement` (`@Transactional`) ← `ProductRepository.findByIdAndDeletedFalse` ← `StockBalanceRepository.findByProductIdForUpdate` (`SELECT ... FOR UPDATE`، أو إنشاء `StockBalance` جديد) ← زيادة `balance.onHand` ← `StockMvtRepository.save` (مع `balanceAfter = balance.onHand`) و `StockBalanceRepository.save` ← `publishEvent(StockMovementPostedEvent)` ← **DB commit** ← إشعار الـ `AFTER_COMMIT` listeners ← الرد بـ **201** `StockMovementResponse`.

### 2. الموظف بيسجل حركة OUT

`StockController.postMovement` ← `StockLedgerServiceImpl.postMovement` ← قفل `StockBalance` بـ `findByProductIdForUpdate` ← فحص `balance.onHand - quantity < 0` (لو أقل من 0 ومش `COUNT_ADJUSTMENT` بيرمي `InsufficientStockException` ← **409 Conflict** + rollback) ← خصم `balance.onHand` ← حفظ `StockMvt` و `StockBalance` ← نشر الـ event ← **DB commit** ← الرد بـ **201** `StockMovementResponse`.

### 3. الموظف بيستلم بضاعة

`StockController.receiveStock` ← `StockLedgerServiceImpl.receiveStock` ← قفل `StockBalance` ← زيادة `balance.onHand` ← بناء `StockMvt` بـ `typeMvt = IN` و `reason = PURCHASE_RECEIPT` و `sourceType = "PURCHASE_ORDER"` (لو فيه `purchaseOrderId`) و `unitCost` و `balanceAfter` ← حفظ `StockMvt` و `StockBalance` ← نشر الـ event ← **DB commit** ← الرد بـ **201** `StockMovementResponse`.

### 4. الموظف بيعمل جرد فعلي

`StockController.recordCount` ← `StockCountServiceImpl.recordCount` ← قفل `StockBalance` ← لقطة `systemQty = balance.onHand` ← حساب `variance = countedQty - systemQty` ← لو `variance != 0`: حفظ `StockMvt` (IN أو OUT، `reason = COUNT_ADJUSTMENT`، `balanceAfter = countedQty`)، وتحديث `balance.onHand = countedQty`، ونشر الـ event ← حفظ `StockCount` بالـ `countedBy` من `AuditorAware` ← **DB commit** ← الرد بـ **201** `StockCountResponse`.

### 5. المدير بيطلب المنتجات الناقصة

`StockController.getLowStock` (مديرين فقط) ← `StockLedgerServiceImpl.getLowStockItems` (`readOnly = true`) ← `findLowStockBalances` (`on_hand <= alert_threshold` على المنتجات النشطة) ← `StockBalanceMapper.toLowStockResponse` ← الرد بـ **200** `List<LowStockItemResponse>`.

### 6. المدير بيطلب تاريخ الحركات

`StockController.getMovementHistory(id, type, from, to, page, size)` ← `StockLedgerServiceImpl.getMovementHistory` (`readOnly = true`) ← `ProductRepository.findByIdAndDeletedFalse` ← `StockMvtRepository.findAll(Specification, PageRequest)` مرتبة بـ `occurredAt DESC` ← `StockMvtMapper::toMovementResponse` ← الرد بـ **200** `PageResponse<StockMovementResponse>`.

### 7. المدير بيعمل recompute للرصيد

`StockController.recomputeBalance(id)` (مديرين فقط) ← `StockLedgerServiceImpl.recomputeBalance` (`@Transactional`) ← قفل `StockBalance` ← `sumInQuantityByProductId` و `sumOutQuantityByProductId` ← `balance.onHand = totalIn - totalOut` ← `findAllByProductIdOrderByOccurredAtAsc` وإعادة حساب `balanceAfter` لكل حركة ← حفظ الرصيد والحركات ← الرد بـ **200** `StockBalanceResponse`.

## Architectural Decisions & Important Concepts

### Append-Only Ledger مقابل Mutable Balance Projection

لو حسبنا الرصيد كل مرة بـ `SUM` على جدول `stock_mvts`، الاستعلام هيبقى أبطأ مع زيادة الحركات، والأهم إنه صعب تقفل صف واحد للـ concurrency. عشان كده بنفصل بين:

1. **`stock_mvts` (Source of Truth):** سجل تاريخي غير قابل للتعديل أو الحذف (append-only)، بيحفظ كل حركة بالسبب والفاعل والوقت.
2. **`stock_balances` (Projection):** جدول ملخص فيه الرصيد الحالي (`on_hand`)، للقراءة السريعة وقفل الصف وقت التعديل.

### Pessimistic Locking (`SELECT ... FOR UPDATE`) مع `@Version`

لما اتنين موظفين يسحبوا نفس المنتج في نفس اللحظة، الـ `@Lock(LockModeType.PESSIMISTIC_WRITE)` بيخلي قاعدة البيانات تقفل صف `stock_balances` للـ transaction الأولانية، والتانية تستنى لحد ما الأولى تعمل commit، وبعدين تقرأ الرصيد المحدث. فلو الرصيد بقى 0 التانية تترفض بـ 409. وجود `@Version` بيدي طبقة حماية إضافية لو حصل تعديل من مسار تاني من غير row lock.

### Transactional Consistency

تسجيل الحركة في `stock_mvts` وتحديث `stock_balances` بيتموا جوه نفس الـ `@Transactional`. لو حصل أي خطأ (زي `InsufficientStockException` أو `chk_on_hand_non_negative`)، الاتنين بيتعملهم rollback سوا، وميحصلش أبداً حركة مسجلة من غير تحديث الرصيد أو العكس.

### ليه الجرد الفعلي بيعمل Adjustment Movement؟

الجرد الفعلي (`StockCount`) مينفعش يكتب فوق `stock_balances.on_hand` مباشرةً، لأن ده هيعمل فجوة (drift) بين الرصيد والـ ledger. بدل كده النظام بيحسب الفرق (variance) ويسجل حركة `COUNT_ADJUSTMENT` في الـ ledger تغطي الفرق ده، فبيفضل مجموع الـ ledger مطابق تماماً للرصيد.

### فايدة `recomputeBalance`

لأن `stock_balances` عبارة عن denormalized projection، وجود endpoint للمدير يعيد حساب `on_hand` و `balance_after` من الـ ledger (`SUM(IN) - SUM(OUT)`) بيضمن إننا نقدر نتحقق من سلامة البيانات ونصلح أي انحراف لو حصل في أي وقت.

### ليه الـ Events بتوصل بعد الـ Commit (`AFTER_COMMIT`)؟

لو الـ listener (زي كاشف الشذوذ Anomaly Agent في المراحل الجاية) اشتغل قبل الـ commit أو على transaction هيتعملها rollback، هيقرأ بيانات مش موجودة أو غلط. استخدام `TransactionPhase.AFTER_COMMIT` بيضمن إن الـ event ميتنفذش غير لو الحركة اتثبتت فعلاً في قاعدة البيانات.

### ليه حذف المنتج الناعم مينفعش يمسح تاريخ المخزون؟

حذف المنتج (`ProductServiceImpl.delete`) معناه إيقاف بيع/استخدام الـ SKU في الكتالوج، لكن تاريخ المشتريات والمبيعات والجرد اللي حصلت عليه قبل كده جزء من السجل المالي والمخزني (audit trail) ومينفعش يتغير أو يختفي. ولأن الحذف على `Product` عبارة عن `UPDATE products SET deleted = true` مش `DELETE` حقيقي، الـ Foreign Key في `stock_mvts` بيفضل سليم من غير ما نلمس جدول الحركات.
